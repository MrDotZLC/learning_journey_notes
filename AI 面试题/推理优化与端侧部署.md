## 1. TensorRT 是什么？解决什么问题？

### Q1：什么是 TensorRT？

### 回答：

TensorRT 是 NVIDIA 提供的深度学习推理优化框架，核心目标是在 NVIDIA GPU 上实现低延迟、高吞吐推理。

它不是训练框架，而是负责将训练得到的模型转换成 GPU 高效执行形式。

典型流程：

```
PyTorch / TensorFlow
        |
        v
       ONNX
        |
        v
TensorRT Builder
        |
        v
 TensorRT Engine
        |
        v
 Runtime Execution
        |
        v
       GPU
```

TensorRT 主要做三类优化：

1. **计算优化**

例如：

- Layer Fusion
- Kernel Selection
- 算子重排
- Tensor Core 加速

2. **内存优化**

例如：

- Tensor 生命周期分析
- Memory Reuse
- Workspace 管理

3. **低精度优化**

例如：

- FP16
- INT8
- FP8

相比直接使用 PyTorch eager mode：

- Python 调度开销减少
- 算子融合减少 kernel launch
- 可以选择 GPU 最优 kernel
- 可以使用 Tensor Core

---

### Q2：TensorRT 和 CUDA、cuDNN 的关系是什么？

### 回答：

三者处于不同抽象层。

|组件|作用|
|---|---|
|CUDA|GPU 编程模型，提供 kernel 开发能力|
|cuDNN|深度学习基础算子库，例如 convolution|
|TensorRT|推理优化框架，负责模型级优化和调度|

关系：

```
TensorRT
    |
    | 调用
    |
 cuDNN / cuBLAS / CUTLASS / CUDA Kernel
    |
    |
 NVIDIA GPU
```

例如 Transformer：

Linear：

```
TensorRT
   |
   +-- cuBLAS GEMM
```

Attention：

```
TensorRT
   |
   +-- TensorRT Plugin
          |
          +-- CUDA Kernel
```

TensorRT 本身不是重新实现所有 GPU kernel，而是负责图优化和选择执行方案。

## 2. TensorRT Engine 构建流程

---

### Q3：TensorRT 从 ONNX 到 Engine 的完整流程？

#### 回答：

主要经过：

```
ONNX Model

↓

Network Definition

↓

Parser

↓

Optimization

↓

Builder

↓

Serialized Engine

↓

Runtime Deserialize

↓

Execution Context

↓

Inference
```

具体过程：

---

#### 1. ONNX Parser

TensorRT 首先解析 ONNX Graph。

例如：

```
MatMul
 |
Add
 |
Gelu
```

转换成 TensorRT Network：

```
INetworkDefinition
```

---

#### 2. Graph Optimization

TensorRT 会进行：

#### Layer Fusion

例如：

Transformer 中：

```
MatMul
 +
Bias
 +
Activation
```

融合：

```
Fused GEMM Kernel
```

减少：

- kernel launch
- global memory read/write

---

#### 3. Tactic Selection

这是 TensorRT 一个重要机制。

一个算子可能存在多个实现：

例如 GEMM：

方案 A：

```
cuBLAS GEMM
```

方案 B：

```
CUTLASS Kernel
```

方案 C：

```
Tensor Core Kernel
```

TensorRT 会 benchmark：

```
candidate kernels

↓

measure latency

↓

select fastest tactic
```

最终写入 Engine。

---

#### 4. Engine Serialization

优化完成后：

```
TensorRT Engine
```

保存：

- 网络结构
- kernel选择结果
- workspace需求
- Tensor信息

运行时无需重新优化。

---

### Q4：为什么 TensorRT Engine 构建比较慢，但是推理快？

#### 回答：

因为 TensorRT 把大量优化工作提前到了 build 阶段。

Build阶段：

```
模型分析

↓

算子融合

↓

kernel搜索

↓

性能benchmark

↓

生成执行计划
```

Runtime阶段：

```
加载engine

↓

执行固定kernel
```

所以：

- Build 时间增加
- 推理时间降低

这种设计属于：

> Ahead-of-Time Optimization

类似 C++ 编译：

```
源码
 |
编译优化
 |
机器码
 |
快速执行
```

## 3. TensorRT Runtime

---

### Q5：TensorRT Runtime 推理过程是什么？

#### 回答：

Runtime 主要包括：

#### 1. Deserialize Engine

加载：

```
.engine文件
```

生成：

```
ICudaEngine
```

---

#### 2. 创建 Execution Context

因为同一个 Engine 可以多个执行实例。

例如：

```
Engine

 |
 +-- Context 1 GPU stream 0
 |
 +-- Context 2 GPU stream 1
```

---

#### 3. Binding Tensor

输入输出：

```
input tensor address

output tensor address
```

绑定 GPU memory。

---

#### 4. enqueue Execute

提交：

```
context.enqueueV3()
```

执行 GPU kernel。

---

### Q6：Engine 和 Execution Context 区别？

#### 回答：

这是高频问题。

|对象|作用|
|---|---|
|Engine|静态执行计划|
|Execution Context|一次推理执行状态|

类比：

```
Engine = 程序代码

Context = 程序运行实例
```

Engine 保存：

- 网络结构
- kernel选择
- 权重

Context 保存：

- runtime状态
- tensor地址
- workspace

如果多线程推理：

通常：

```
一个线程
一个Execution Context
```

## 5. TensorRT 中的 Layer Fusion

---

### Q8：什么是 TensorRT Layer Fusion？

#### 回答：

Layer Fusion 是将多个连续算子合并为一个 kernel。

目标：

减少：

1. kernel launch次数
2. global memory访问

例如 Transformer FFN：

原始：

```
Linear1

↓

GELU

↓

Linear2
```

融合后：

```
Fused MLP Kernel
```

GPU执行：

```
load input

compute GEMM

apply activation

write output
```

减少中间 Tensor 写回显存。

---

### Q9：为什么 Fusion 可以提升性能？

#### 回答：

GPU性能瓶颈通常不是单纯 FLOPS。

很多 Transformer 算子属于：

> Memory Bound

例如：

LayerNorm：

计算量：

较低。

但是：

```
读取hidden

计算mean/std

写结果
```

主要消耗显存带宽。

Fusion：

```
减少一次global memory round trip
```

因此提升明显。

---

### Q12：TensorRT 支持哪些精度？

#### 回答：

主要：

|Precision|特点|
|---|---|
|FP32|精度最高，速度慢|

---

### Q13：为什么 FP16 可以提升性能？

#### 回答：

因为 NVIDIA GPU Tensor Core 对 FP16 有专门硬件支持。

例如：

FP32：

```
CUDA Core
```

FP16：

```
Tensor Core MMA
```

Tensor Core 一次处理更多矩阵乘。

同时：

FP16 数据：

```
memory size = FP32的一半
```

因此：

- 显存占用降低
- bandwidth压力降低

例如：

FP32：

```
[-5,5]
```

映射：

```
INT8 [-127,127]
```

Calibration过程：

输入代表性数据：

```
calibration dataset

↓

统计activation distribution

↓

计算scale

↓

生成INT8 engine
```

### Q15：INT8 Calibration有哪些方法？

#### 回答：

常见：

| 方法                     | 特点              |
| ---------------------- | --------------- |
| Entropy Calibration    | KL散度，TensorRT常用 |

### Q16：为什么 INT8 会损失精度？

#### 回答：

因为量化存在：

```
FP32

↓

↓

```

这是离散映射。

误差来源：

1. activation range估计误差
2. outlier影响
3. 参数精度降低

LLM中通常需要：

- SmoothQuant
- GPTQ
- AWQ

降低量化误差。

## 10. LLM 推理基本流程

### Q19：大语言模型一次生成过程包含哪些阶段？

#### 回答：

LLM 推理通常分为两个阶段：

1. **Prefill（预填充阶段）**
2. **Decode（逐 token 生成阶段）**

例如输入：

```
今天天气怎么样
```

模型首先处理整个输入：

```
今天 天气 怎么样
```

得到第一个输出 token。

之后：

```
天气
```

每次只生成一个新的 token。

---

### Q20：Prefill 和 Decode 的区别是什么？

#### 回答：

两者计算特点不同。

|阶段|输入|计算特点|主要瓶颈|
|---|---|---|---|
|Prefill|完整 prompt|大矩阵计算|计算密集|
|Decode|单 token|重复访问 KV Cache|显存带宽|

---

Prefill：

输入长度为 $S$。

Attention：

```
Q × K
```

一次处理整个序列。

GPU：

- batch 大
- GEMM 大
- Tensor Core利用率高

因此通常：

> Prefill 更偏 compute bound

---

Decode：

每次只输入：

```
一个token
```

但是需要读取历史：

```
KV Cache
```

例如：

```
当前token

↓

读取过去4096个token KV

↓

Attention
```

所以：

> Decode 更偏 memory bound

---

### Q21：为什么 LLM Decode 阶段慢？

#### 回答：

主要原因不是计算量，而是：

> 每生成一个 token 都需要访问历史 KV Cache。

例如：

LLaMA：

每层保存：

```
Key
Value
```

如果上下文：

```
4096 tokens
```

生成：

```
第4097 token
```

需要读取：

```
前4096 token KV
```

随着序列增长：

KV Cache越来越大。

瓶颈：

- HBM bandwidth
- memory latency

---

## 11. KV Cache

---

### Q22：为什么 Transformer 推理需要 KV Cache？

#### 回答：

Self Attention：

每个 token 都需要：

```
Q × K^T
```

和：

```
Attention × V
```

如果没有 KV Cache：

生成第N个token：

需要重新计算：

```
token1~tokenN-1
```

所有：

- Key
- Value

复杂度接近：

```
O(N²)
```

KV Cache：

保存历史：

```
K1,V1

K2,V2

...

KN,VN
```

生成新token：

只计算：

```
Qnew

Knew

Vnew
```

然后：

```
append KV Cache
```

避免重复计算。

---

### Q23：KV Cache 存储什么？

#### 回答：

保存每层 Attention 的：

```
Key Tensor

Value Tensor
```

结构：

```
Layer

 ├── KV Cache
 │
 ├── Key
 │     [batch, head, seq, dim]
 │
 └── Value
       [batch, head, seq, dim]
```

不同模型：

- MHA
- MQA
- GQA

KV Cache大小不同。

---

### Q24：KV Cache 为什么占用大量显存？

#### 回答：

因为：

KV Cache：

```
batch × layer × seq_len × hidden_size × precision
```

随着：

- batch增加
- context增加
- layer增加

线性增长。

例如：

70B模型：

几十GB KV Cache 很常见。

因此：

LLM部署优化重点之一：

> 降低KV Cache显存占用，提高batch能力。

---

## 12. Paged KV Cache

---

### Q25：什么是 Paged KV Cache？

#### 回答：

Paged KV Cache 是 TensorRT-LLM、vLLM 等框架中的重要优化。

核心思想：

> 像操作系统分页管理内存一样，把 KV Cache 切成固定大小 block。

传统：

连续分配：

```
Request1

[====================]
```

问题：

不同请求长度不同：

导致：

- memory fragmentation
- 预留浪费

Paged KV Cache：

```
KV Block

[Block0]
[Block1]
[Block2]
[Block3]
```

不同请求：

通过：

```
block table
```

映射。

---

### Q26：Paged KV Cache 如何减少显存浪费？

#### 回答：

传统：

假设最大长度：

4096。

用户实际：

1000 token。

仍需要：

```
4096空间
```

Paged：

按block申请：

```
实际1000 token

↓

申请几个block
```

因此：

提高：

- KV Cache利用率
- batch size

---

### Q27：Paged KV Cache 和虚拟内存有什么类似？

#### 回答：

思想类似。

CPU：

```
virtual address

↓

page table

↓

physical memory
```

LLM：

```
sequence position

↓

block table

↓

KV memory block
```

区别：

GPU KV Cache：

没有操作系统参与。

由：

- runtime scheduler
- memory manager

管理。

---

## 13. Continuous Batching

---

### Q28：什么是 Continuous Batching？

#### 回答：

Continuous Batching（连续批处理）是 LLM 推理提高吞吐的重要技术。

传统 Batch：

一次提交：

```
request1
request2
request3
```

必须：

```
全部完成

↓

下一批
```

问题：

生成长度不同：

短请求等待长请求。

---

Continuous Batching：

动态调度：

```
时间0:

A B C

时间5:

B完成

↓

加入D
```

GPU持续执行。

---

### Q29：Continuous Batching 为什么适合 LLM？

#### 回答：

因为 LLM Decode：

每个请求：

```
每步生成一个token
```

天然是：

iteration-based。

每轮：

```
scheduler选择活跃request

↓

batch decode

↓

更新KV Cache

↓

继续
```

---

### Q30：Continuous Batching 和 Dynamic Batching区别？

#### 回答：

|技术|特点|
|---|---|
|Static Batch|固定batch|
|Dynamic Batch|等待请求组成batch|
|Continuous Batch|运行过程中动态加入退出|

Continuous Batch 更适合：

- 长文本生成
- Chat服务
- Agent

---

## 14. TensorRT-LLM Inflight Batching

---

### Q31：TensorRT-LLM中的 Inflight Batching 是什么？

#### 回答：

Inflight Batching 是 TensorRT-LLM 对 Continuous Batching 的实现。

核心：

Scheduler动态维护：

```
running requests
waiting requests
finished requests
```

每个decode step：

执行：

```
1. 收集当前token请求

2. 拼batch

3. 执行engine

4. 更新KV Cache

5. 淘汰完成请求

6. 加入新请求
```

---

### Q32：Continuous Batching 最大收益是什么？

#### 回答：

主要提升：

#### GPU利用率

传统：

```
request A:

GPU busy

↓

等待结束

↓

GPU idle
```

Continuous:

```
A结束

↓

B立即进入
```

减少：

- bubble
- idle time

## 16. FlashAttention

---

### Q34：FlashAttention 优化思想是什么？

#### 回答：

FlashAttention核心：

> 不改变Attention数学结果，通过减少HBM访问提升性能。

普通Attention：

```
QK

↓

写score matrix到显存

↓

Softmax

↓

读取

↓

乘V
```

FlashAttention：

利用：

```
SRAM / Shared Memory
```

分块计算：

```
Q block

×

K block

↓

online softmax

↓

accumulate V
```

避免：

```
N×N attention matrix
```

写回显存。

---

### Q35：FlashAttention为什么快？

#### 回答：

因为 Attention 通常不是算力不足，而是：

> 显存访问过多。

优化：

减少：

```
HBM read/write
```

提高：

```
Arithmetic Intensity
```

## 17. Tensor Parallel

---

### Q36：什么是 Tensor Parallel？

#### 回答：

Tensor Parallel（TP）是把一个模型层切分到多个 GPU。

例如 Linear：

```
Y=XW
```

如果：

```
GPU数量=P
```

则：

```
W切成P份
```

每个GPU：

计算：

```
XWi
```

最后：

合并结果。

---

### Q37：Tensor Parallel为什么需要通信？

#### 回答：

因为：

不同GPU只拥有部分权重。

计算后需要：

同步结果。

例如：

Column Parallel Linear：

每个GPU：

```
计算部分output
```

需要：

```
AllGather
```

Row Parallel：

需要：

```
AllReduce
```

---

### Q38：Tensor Parallel 的瓶颈是什么？

#### 回答：

通信。

当：

GPU数量增加：

计算减少：

但是：

NCCL通信增加。

例如：

8 GPU：

计算：

约1/8

但是通信：

不能无限降低。

因此：

TP通常适合：

单机多GPU。

---

## 18. Pipeline Parallel

---

### Q39：什么是 Pipeline Parallel？

Pipeline Parallel（PP）按模型层切分。

24层模型：

```
Layer0-7

Layer8-15

GPU2:

Layer16-23
```

输入依次流过。

---

### Q40：Pipeline Parallel问题是什么？

#### 回答：

Pipeline Bubble。

例如：

第一阶段启动：

```
GPU0 busy

GPU1 idle
```

最后：

```
GPU0 idle
```

需要：

micro batch

## 22. 模型量化基础

---

### Q44：什么是模型量化？为什么推理需要量化？

#### 回答：

模型量化是将高精度浮点模型转换为低精度表示，例如：

```text
FP32 → FP16
FP32 → INT8
FP16 → INT8
```

目的：

1. 降低显存占用

例如：

- FP32 一个参数占 4 Byte
- FP16 一个参数占 2 Byte
- INT8 一个参数占 1 Byte

2. 提升计算性能

现代 NVIDIA GPU：

- FP16
- BF16
- INT8
- FP8

都有专用 Tensor Core。

3. 提升部署能力

端侧 GPU：

例如 Jetson：

显存有限，需要降低：

- 模型权重
- KV Cache
- Activation

---

### Q45：量化的核心原理是什么？

#### 回答：

核心思想：

> 使用有限bit表示连续浮点值。

例如：

FP32：

```text
-3.5 ~ 4.2
```

映射：

```text
INT8

-127 ~ 127
```

需要一个 scale：

简单理解：

```text
真实值 = 整数值 × scale
```

量化过程：

```text
FP32 Tensor

↓

统计范围

↓

计算scale

↓

转换INT8

↓

INT8 Kernel执行
```

---

## 23. PTQ 与 QAT

---

### Q46：PTQ 和 QAT 区别是什么？

#### 回答：

|方法|特点|
|---|---|
|PTQ(Post Training Quantization)|训练后直接量化|
|QAT(Quantization Aware Training)|训练过程中模拟量化|

---

### PTQ

流程：

```text
训练完成模型

↓

Calibration

↓

生成INT8模型
```

优点：

- 简单
- 无需重新训练

缺点：

- 精度损失较大

---

### QAT

训练时：

模拟：

```text
FP32

↓

Fake Quant

↓

FP32 Backprop
```

让模型提前适应量化误差。

优点：

精度更高。

缺点：

需要训练资源。

## 24. LLM量化方法

---

### Q47：为什么LLM量化比CNN困难？

#### 回答：

主要原因：

LLM存在：

#### 1. Activation outlier

Transformer中部分activation：

幅值非常大。

例如：

```text
[-1,1]

但是存在：

100
```

INT8：

scale被大值影响。

导致：

正常值精度下降。

---

#### 2. 长序列误差累积

LLM生成：

每个token依赖之前结果。

小误差可能逐渐放大。

## 25. SmoothQuant

---

### Q48：SmoothQuant解决什么问题？

#### 回答：

SmoothQuant解决：

> LLM activation outlier导致INT8量化困难的问题。

核心思想：

将量化难度：

从 activation 转移到 weight。

原始：

```text
Activation难量化

Weight容易量化
```

通过数学变换：

```text
Activation缩小

Weight放大
```

保持：

```text
W × X
```

结果不变。

最终：

weight和activation都容易INT8。

## 26. GPTQ

---

### Q49：GPTQ是什么？

#### 回答：

GPTQ 是一种大模型权重量化方法。

特点：

- Post Training Quantization
- 基于二阶信息
- 通常用于4bit weight-only量化

核心：

量化一个权重后：

调整剩余权重补偿误差。

目标：

减少：

```text
W_fp16

↓

W_int4
```

之间误差。

---

### Q50：GPTQ为什么适合LLM？

#### 回答：

因为LLM：

主要计算：

Linear层。

权重占显存大部分。

GPTQ：

只量化weight：

```text
W INT4

X FP16
```

计算：

INT4 × FP16。

优势：

- 权重大幅降低
- Activation保持精度

AWQ（Activation-aware Weight Quantization）
