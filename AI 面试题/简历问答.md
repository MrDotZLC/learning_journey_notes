## 项目1 LLM推理GPU Kernel与算子优化
### Q1：介绍与为什么写这么多版本的GEMM
答：为了理解GEMM 从Naive到高性能实现的优化过程，从单精度FP32 的CUDA Core 实现 到 FP16 的WMMA/MMA/CUTLASS。

CUDA Core里：利用 Shared Memory+Tiling、线程粗粒度化（线程多干点活）、向量化加载、bank conflict消除、双缓冲流水线、大分块调整”SM占用率、Shared Memory、Register使用量“都达到架构最合适的水平。

WMMA/MMA里：利用Shared Memory+Tiling、调整warp tile+向量化加载、双缓冲流水线。MMA里有些特殊的是，用ldmatrix原语代替手动加载数据。

CUTLASS框架比较成熟，底层封装了mma原语，自动执行最优的方案，这里我除了实现Naive写法，还实现了自定义Epilogue实现fused bias broadcast 也就是线性带偏置的乘加操作。追问为什么不用其他的Epilogue，回答 试了带Relu 的Epilogue，因为架构的缓存行不支持这个操作，就没再是别的了。

主要使用 Roofline 分析不同版本的瓶颈，没有追求极限性能就没用ncu分析。

### Q2：你这个项目最大的技术难点是什么？
答：最大难点不是 CUDA Kernel 能不能写出来，而是确定每个阶段真正的性能瓶颈，并选择对应的优化手段。

例如 
0. Naive GEMM 的主要问题是Global Memory访问和数据复用不足->  
1. Tiling 通过Shared Memory 提高了A/B tile 的复用，此时瓶颈主要在线程计算强度低->  
2. 矩阵规模较大时，每个线程只计算一个元素，寄存器利用不充分，而时延隐藏依赖Warp切换，导致计算 Warp 时常处于饥饿状态，优化的做法是**线程粗粒化分块**，每个线程处理一块元素，中间值放在寄存器，既提高了数据复用，又隐藏了访存时延，此时又发现吞吐效率不及预期，问题在于搬运开销->  
3. 搬运时使用向量化加载，实现访存合并，此外shared memory读取效率较低，存在bank 冲突和shared memory 加载与计算串行->
4. 消除bank 冲突：padding、swizzle，收益低甚至负收益，因为warp调度和缓存命中都会降低bank冲突的危害，额外的计算也会降低收益。
5. 采用双缓冲流水线实现smem 加载和计算异步，隐藏数据搬运时延，注意与**粗粒度分块**竞争寄存器资源，可降低粗粒度分块尺寸。

所以我的优化过程不是单纯不断调参数，而是通过 profiling 判断瓶颈，然后针对瓶颈优化。

### Q3：GEMM 的计算量是多少？
1乘1加-2次计算-2MNK
答：每个输出元素包含1次乘法、1次加法，则 $FLOPS=2MNK$，如果kernel时延为 $t$ 秒，则：

$$TFLOPs=\frac{2MNK}{t \times 10^{12}}$$

### Q4：为什么 GEMM 特别适合 GPU？
**计算并行度；数据复用率；输出元素间独立；tile加载到smem复用；映射到block和Tensor Core。**
答：因为 GEMM 同时具备非常高的计算并行度和数据复用率，$MN$个输出元素之间基本独立，可以映射到 Thread Block/warp；同时 A 和 B 的 tile 可以加载到 Shared Memory，并被多个线程重复使用，从而显著降低 Global Memory traffic。

### Q5：为什么 Naive GEMM 性能差？
**计算访存比低；B 矩阵非连续访问；A/B 数据零复用； Shared Memory；Register**
答：主要问题在于**计算访存比低**，不同线程访问 B 是行间跳跃的，不连续，导致缓存命中率低；相邻线程重复读取Global Memory，数据零复用 ，带宽严重浪费。

核心优化方向是把 Global Memory → Shared Memory → Register 的数据层级利用起来。

### Q6：Tiling 到底解决了什么问题？
**解决访存比低；数据tile；Shared Memory；数据复用**
答：解决访存比低，数据没有被重复利用的问题；设 block 计算 C 的一个 $TM \times TN$ 的 tile，A/B Tile 加载到Shared Memory 供 block 所有线程使用。

### Q7：为什么 Tile 不能无限大？
**资源和成本增加；Warp 占用率**
答：各种与 block 相关的资源和成本会增加，如smem、register、synchronization 成本，Tile 过大会限制 Warp occupancy 占用率。需要对资源和数据复用之间做 trade-off。

### Q8：什么是 Coalesced Memory Access？
**访存事务；地址连续**
答：一个 warp 的线程访问 Global Memory 时，如果访问地址具有良好的连续性，硬件可以将多个线程的访问合并成较少的 Memory Transactions，这就是 Coalesced Access。一个访存事务是 32 个 byte，128 bit。

### Q9：Shared Memory 为什么比 Global Memory 快？
**在 SM 片；bank conflict**
答：smem 位于 SM 片上，访问延迟和带宽特性都明显优于 HBM/Global Memory；bank conflict 会降低有效带宽。常见解决办法：padding、swizzle。

### Q10：为什么还要做 Register Blocking？Shared Memory 不是已经很快了吗？
**独属线程；外积计算；数据复用率**
答：Register Blocking 独属线程比读取 Shared Memory 更快，线程处理多个元素时，把数据加载到 register 上，k 维迭代时采用外积计算，能够提高数据复用率。

### Q11：为什么 Register 用多了反而可能变慢？
**SM 的 Register 有限；Block数下降；Occupancy 下降；可能 Register Spill**
答：因为每个 SM 的 Register File 是有限的，单线程 Register 使用量增加后，一个 SM 能同时驻留的 Thread Block 数量可能下降，Occupancy 降低；如果 Register pressure 过大甚至可能产生 Register Spill，将数据放到 Local Memory（Global Memory 的一部分），性能可能出现明显下降。

### Q12：Double Buffering 是什么？
**2 个 smem；计算和搬运异步；隐藏搬运时延**
答：计算和数据搬运可异步执行，使用 2 个 Shared Memory 存放当前和下一个 Tile 的数据，隐藏搬运时延，同理 Register Fragment 也可以 Double Buffering。

隐藏搬运时延的核心是 Occupancy，大量 Warp 驻留 SM 时，一个 Warp 发起访存请求时，Warp Scheduler 立刻切换可计算的 Warp，将其发射到ALU/LSU 执行计算或者加载。

### Q13：为什么隐藏搬运时延，而不是计算时延？
**搬运时延大；计算效率高；计算时延固定**
答：搬运延迟的数量级远大于计算，浮点乘加是高度流水化的，计算时延时固定的、可预测的。

### Q14：Double Buffering 一定能提高性能吗？
**Memory-Bound；Occupancy 降低；Profiling 验证**
答：不一定，Double Buffering 主要能提高计算效率，解决 Memory-Bound。如果 Kernel 已经 Compute-Bound，Double Buffering 可能反而因为资源占用而降低 Occupancy，起到反作用。是否使用，要通过 Profiing 验证，而不是固定模板。

### Q15：WMMA、MMA、CUDA Core 有什么区别？
答：
CUDA Core：通用标量/向量计算
WMMA：CUDA WMMA API，面向 Warp 的 Tensor Core 接口，高层 API 
MMA：硬件指令级 API，更底层地控制 Tensor Core
CUTLASS：CUDA C++ 模板，工业级 GEMM 框架，封装了 Tiling、Copy、MMA、Pipline等组件，能够自动优化。

Tensor Core：支持混合精度乘加计算的硬件单元，计算粒度更大。

### Q16：为什么 Tensor Core 比 CUDA Core 快？
**专门矩阵乘加的硬件单元；单指令大量乘加操作**
答：专门用于矩阵乘加的硬件单元，可以一次指令完成一个矩阵 fragment 的大量乘加操作，而 CUDA Core 一次指令只能完成一个元素的 FMA 浮点矩阵乘计算

### Q17：MMA 为什么要求特定的数据布局和 Shape？
**受 Tensor Core 固定矩阵运算粒度限制**
答：MMA 是底层硬件级 API，对应Tensor Core 固定的 Fragment 尺寸。

调用 Tensor Core 的核心难点是 将各级数据布局转成 Tensor Core 高效计算的布局。

### Q18：FP16 输入一定意味着 FP16 累加吗？
答：不一定，也可输出 FP32

### Q19：你为什么能做到 WMMA/MMA 比 cuBLAS 快 1.6×？
**硬件限制；降级 CUDA Core；优化和调度开销** 
答：因为本地硬件限制，GPU 是 Turing 架构且去掉了 Tensor Core。我的MMA/WMMA 实际走的是 CUDA Core，是通过配置 SM80 强行运行的。cuBLAS 由于防御性优化，会先尝试优化和调用 Tensor Core，失败后才降级为 CUDA Core，所以时延反而下降很多。

这也反映了，算子的效率不能只考虑优化策略，还要结合硬件条件，最终以Profiling 验证结果去决定优化方向和策略。

### Q20：你 benchmark cuBLAS 的时候怎么保证公平？
**固定硬件、环境、规模、精度；计时cudaEvent；warmup；多轮测量**
答：固定硬件、环境、数据规模等一切影响因素，确保使用相同的精度；时间测量用cudaEvent；经过充分的 Warmup和多轮测量。

### Q21：为什么不能用 CPU `std::chrono` 直接测 CUDA Kernel？
答：Kernel Launch 是异步的，CPU 无法计时。

### Q22：什么是 Roofline Model？
答：两个上限描述性能，计算吞吐和内存带宽。性能上限$P \lt min(P_{peak}, BW_{peak} \times AI)$

### Q23：怎么判断一个 Kernel 是 Compute-Bound 还是 Memory-Bound？
答：$AI=\frac{FLOPs}{Byte/s}$ 小于 $AI_{peak}$ 则 Memory-Bound，大于则 Compute-Bound。

### Q24：为什么 GEMM 通常 Compute-Bound，而 FlashAttention 经常强调 Memory-Bound？
**GEMM 数据复用性高；attention 多次 HBM 读写**
答：GEMM 数据复用性高，AI 通常较高。传统 attention 需要多次 HBM 读写中间值。

### Q25：传统 Attention 为什么需要 $O(N^2)$ 显存？
**S 的形状**
答：$S=QK^T$ 的矩阵形状是 $N^2$。所以 $N$ 很大时。性能瓶颈在于中间值的 HBM 读写。

### Q26：FlashAttention 为什么不需要保存完整的 $N\times N$ Attention Matrix？
答：因为采用 Block 和 Tiling，只需要小块尺寸的显存。 

### Q27：Online Softmax 是怎么工作的？
**维护最大值 m 、减去最大值后的指数和 l、未归一化的累计输出 \hat{O}**
答：l 在FA-1中用来归一化累计输出和梯度计算中反推softmax值；在FA-2中延迟归一化，仅用作梯度计算。都是为了避免缓存中间值。
$$l_{all}=l_{a}e^{m_{a}-m_{all}} + \sum_{j \in b} e^{x_j；m_{all}}$$
$$\hat{O}_{all}=\hat{O}_{a} e^{m_{a}-m_{all}} + \sum_{(x_j,V) \in b} e^{x_j；m_{all}}V $$

### Q28：如果后面 block 的 max 更大，前面的结果怎么办？
答：历史部分的归一化和 $l$ 以及未归一化的累计输出 $\hat{O}$ 重新缩放，再当前贡献。

### Q29：FlashAttention 的“优化”到底优化了什么？
**减少 HBM与smem间的数据搬运**
答：减少 HBM ↔ SRAM 的数据搬运，通过 IO-aware tiling 减少 HBM accesses。

### Q30：你用 Nsight Compute 看了哪些指标？
答：Memory 吞吐、SM 吞吐、L2 吞吐、SMEM 吞吐、活跃 Warp 比例（Occupancy）、每线程Register、每block Smem、Tensor Core使用情况，还有Nsight Compute 给出的建议。

### Q31：如果 Nsight 显示 Occupancy 只有 30%，是不是一定要优化？
答：不一定，要看Tensor Core使用情况，计算满负荷则不需要优化Occupancy。

### Q32：一个 Thread Block 会运行在哪个 SM？
答：一个block只停留在单个SM中。

### Q33：一个 Warp 有多少线程？
**32；调度复杂度、合并缓存、分支发散、延迟隐藏能力、工程成本**
答：32个，是SMIT的基本单位，这是调度复杂度、访存合并、分支发散、延迟隐藏能力、工程成本之间的工程最优平衡点。

### Q34：Warp Divergence 是什么？
**有效并行度下降；Warp 重组；warp efficiency**
答：kernel中条件判断使得部分线程空闲，导致有效并行度下降。尽量保持同一指令内无条件分支，或者使用Hopper架构，其动态warp重组会临时合并相同路径的线程为临时warp，减少线程空闲。
可通过warp 效率 查看warp每条指令上平均活跃的线程数，一般可直接查看线程束状态统计和Source页面，会直观显示哪里存在低branch效率。

### Q35：什么是 Bank Conflict？
**同线程同时访问相同Bank；访问串行化；广播**
答：Shared Memory 被分为32个Bank，如果同个 warp 不同线程同时访问相同的Bank，则会访问串行化。多线程同时访问同地址是例外，因为硬件会广播这个地址的数据，不会冲突。

可通过共享内存效率和bank计数来分辨是否有冲突，最直观的可查看 Source页面，一般会直接告知冲突位置和路数。

### Q36：CUTLASS 和 cuBLAS 有什么区别？

答：
cuBLAS 是 NVIDIA 官方提供的闭源、黑盒式高性能线性代数库，开箱即用、性能极致，适合标准的矩阵乘法等运算；
CUTLASS 是开源、白盒式的 C++ 模板元编程框架，它把 GEMM 拆解成可自由组合的模块（如分块大小、流水线、精度、Epilogue 融合等），灵活度极高但调优门槛也高。

### Q37：CUTLASS 为什么性能这么高？
**可调优组件；层次化分解策略；可配置的调优参数；硬件特征；榨干TensorCore性能**
答：因为它对GEMM的每一层都开放为可调优的组件，从层次化的分解策略到可配置的调优参数，允许开发者精细调整，还能深度硬件特性，榨干Tensor Core的每一份性能。

### Q38：既然你已经会写 CUDA Kernel，为什么还要学习 CUTLASS？
**理解底层机制；更成熟高效**
答：因为手写 Kernel 可以理解底层机制，但实际工业 GEMM 涉及大量硬件和边界条件，例如不同 GPU Architecture、Tile Shape、MMA instruction、Data Layout、Pipeline、Epilogue、Alignment 等，如果全部从零实现开发成本非常高。

CUTLASS 提供了模块化抽象，使这些底层机制可以组合和调优，同时仍然保留对数据布局、Tile 和 Pipeline 的控制。

### Q39：生产环境中为什么不直接用 cuBLAS？
**灵活性差；不支持自定义算子。**
答：标准 GEMM，通常优先使用 cuBLAS；存在特殊 Shape、特殊 Layout、Fusion、量化格式或特定模型算子需求时，自定义 Kernel 能获得额外收益。

### Q40：GEMM 在 Transformer 中主要出现在哪里？
答：Linear、FFN、Projection

### Q41：为什么 LLM Decode 阶段的 GEMM 和传统大 Batch GEMM 不一样？
**规模可能小；计算效率不高**
答：Decode 阶段，不同请求的输入长度不一定相同，如果Batch小，计算效率不一定高。

### Q42：你的 GEMM 速度提升 1.6×，是不是意味着 LLM inference 也提升 1.6×？
答：不是，因为LLM inference 还受到很多因素的影响，例如：attention、KV Cache、Memory Bandwidth、Kernel Launch、Communication、Communication、Batch size等。

**硬件、环境、规模、精度、warmup；多轮测量；时延、吞吐；性能指标**
答：我固定了硬件、环境、规模、精度、warmup，并且进行了多轮测量，同时对时延、吞吐等性能进行验证，足以证明不是偶然。

答：这个数字主要体现了优化过程，而且是多种参数组合下的最优情况，意义在于不断分析和优化的过程。

## 项目2 CUDA Kernel Benchmark评测框架

### Q1：你为什么要做这个 Benchmark Framework？
**Benchmark 不统一 - 内存管理、数据拷贝、warmup、kernel 分发、计时、正确性校验 - 多轮测量、性能统计、数据导出**
答：我做这个框架主要是为了解决 CUDA Kernel 优化过程中 Benchmark 不统一的问题。最初不同 Kernel 的测试代码可能分别处理 `cudaMalloc`、数据拷贝、Warmup、计时和正确性校验，容易出现测试逻辑不一致，导致不同实现之间无法公平比较。
所以我把这些公共逻辑抽象成一个统一的 Benchmark Harness，做一些工程化的工作，如性能统计和数据导出等功能，这样优化 Kernel 时只需要关注 Kernel 本身，Benchmark 层负责保证测试方法一致。

### Q2：你的 Benchmark Framework 和直接写一个 `main()` 测 CUDA Kernel 有什么区别？
**工程与算法分隔**
答：把控制变量做得规范化，把工程与算法分隔开，避免逻辑混淆。

### Q3：为什么 GPU Kernel Benchmark 不能直接使用 `std::chrono`？
**CPU、GPU异步**
答：因为 CUDA Kernel Launch 是异步的，CPU 发起 Kernel 后通常不会等待 GPU 执行完成，如果直接用 `std::chrono` 测量 Kernel Launch 前后的 CPU 时间，测到的主要是 Launch Overhead，而不是 GPU Kernel 的执行时间。

更适合使用 CUDA Event，因为 Event 在 GPU Stream 中记录，可以测量 GPU 时间线上的两个事件之间的 elapsed time。

### Q4：CUDA Event 为什么可以测 Kernel 时间？
**CUDA Stream 中插入时间戳**
答：CUDA Event 本质上是在 CUDA Stream 中插入时间戳，两个 Event 之间的时间差对应 GPU Stream 上相关工作的执行时间，因此比 CPU wall-clock 更适合测 Kernel latency。

Event 测量的是 **GPU execution timeline 上的时间**，不等于完整的端到端 latency。

### Q5：为什么要 Warmup？
**状态不稳定 - 初始化、频率调整开销**
答：第一次 Kernel 执行通常不能代表稳定状态，因为可能存在 CUDA Context 初始化、Kernel 加载、缓存建立、频率调整等额外开销，所以需要先执行若干 Warmup Iteration，再进行正式测量。

热身轮次没有统一固定值，需要根据 Kernel 和测试环境判断，通常通过多轮执行观察 latency 是否进入稳定区间。

### Q6：为什么 Kernel Benchmark 经常使用 Mean / Median，而不是只看 Min？
**Min理想的执行时间 - Mean异常值影响 - Median对outlier 鲁棒 - P95/P99**
答：Min 可以反映比较理想的执行时间，但对实际服务场景的代表性有限；Mean 容易受到异常值影响，而 Median 对少量 outlier 更鲁棒。因此实际 Benchmark 通常至少观察 Median，同时结合 P95/P99 分析尾延迟。

### Q7：如果 Kernel A 平均 latency 0.5 ms，Kernel B 0.6 ms，能不能直接说 A 快 20%？
**推荐用加速比。**
答：可以，但需要准确表达。推荐用加速比。

### Q8：你的 Benchmark 如何计算 TFLOPS？
答：根据理论 FLOPs 和实测 latency 计算出来的 throughput 指标

### Q9：Attention 的 TFLOPS 怎么算？
**$QK^T$ 和 $SV$  -  $2 \times 2N^2d = 4N^2d$**
答：主要计算量体现在$QK^T$ 和 $SV$ ，均为 $2N^2d$，共 $4N^2d$。实际每步计算都会影响吞吐，更适合作为性能指标。
