## 1. 推理系统 / 框架设计

---

### 1.1 推理框架的整体架构包含哪些核心模块？

**【锚点】** 接入 → 调度 → 执行 → 后处理，四层分离。

**【答案】**

| 模块                        | 职责                                      |
| ------------------------- | --------------------------------------- |
| **Frontend / API Server** | HTTP/gRPC 接入，请求解析、tokenization          |
| **Scheduler**             | 请求队列管理、batching 决策、抢占策略                 |
| **Engine / Executor**     | 模型权重管理、KV Cache 管理、kernel 调度            |
| **Worker**                | 单 GPU 上的实际计算（forward pass）              |
| **Sampler**               | logits → token（temperature、top-p、top-k） |
| **Detokenizer**           | token id → 文本，流式输出                      |

**【深挖】**

- vLLM 中 `LLMEngine` 对应调度层，`Worker` 对应执行层，通过 `ray` 或 `multiprocessing` 实现多卡分布。
- 调度器与执行器解耦的意义：调度决策不需要等 GPU 完成，可流水线化。

---

### 1.2 推理引擎执行流程（加载 → 调度 → 执行 → 输出）

**【锚点】** 权重加载一次，每步调度决定 batch，每步执行一次 forward，流式 detokenize。

**【答案】**

```
1. 初始化：加载权重到 GPU HBM，分配 KV Cache 内存池
2. 请求入队：tokenize → SequenceGroup，加入 waiting queue
3. 调度（每 iteration）：
   - 从 waiting/swapped/running 三个队列中选出本轮 batch
   - 分配 / 换出 KV Cache blocks
4. 执行：
   - Prefill（首次）：处理整个 prompt，并行计算
   - Decode（后续）：每步生成 1 token，自回归
5. 采样：softmax + sampling → next token id
6. 输出：detokenize，流式推送给客户端；若 EOS 则标记完成
```

**【深挖】**

- Prefill 和 Decode 在同一个 forward 中通过 attention mask 区分，PagedAttention 统一管理两者的 KV blocks。

---

### 1.3 计算图（Graph）与运行图（Runtime Graph）的区别？

**【锚点】** 计算图是静态拓扑描述，运行图是带内存绑定的可执行实例。

**【答案】**

- **计算图**：描述算子拓扑与数据依赖，不绑定具体内存地址（如 ONNX、TorchScript IR）。
- **运行图**：计算图 + 内存分配 + 算子实现选择（kernel selection），可直接执行。

**【深挖】**

- TensorRT 的 `engine` 就是编译后的运行图，绑定了具体 batch size、数据类型、内存布局。
- 分离的意义：同一计算图可针对不同硬件生成不同运行图（kernel fusion 策略不同）。

---

### 1.4 动态图 vs 静态图的差异与优化意义？

**【锚点】** 动态图逐 op 执行便于调试，静态图整图可见便于全局优化。

**【答案】**

|维度|动态图（Eager）|静态图（Graph）|
|---|---|---|
|执行时机|逐算子立即执行|先构图后执行|
|调试难度|低（Python 级别）|高（图级别）|
|优化空间|小（单算子）|大（跨算子 fusion、内存复用）|
|控制流|原生 Python|需要特殊处理（cond、while）|

**【深挖】**

- `torch.compile` 用 Dynamo 捕获 Python 控制流，FX Graph 表示，Inductor 后端生成 Triton/C++ kernel，兼顾灵活性与优化。

---

### 1.5 为什么推理优化通常先转静态图？

**【锚点】** 静态图使 shape 已知，才能做 kernel fusion、常量折叠、内存规划。

**【答案】**

转静态图的收益链：

1. **Shape 固定** → 可做 kernel fusion（避免中间 tensor 写回 HBM）
2. **数据流可见** → 死代码消除、常量折叠
3. **内存生命周期已知** → 静态内存规划，零碎分配变为预分配
4. **支持 INT8/FP8 量化校准**（需要固定 shape 做 calibration）

**【深挖】**

- TensorRT 要求固定 shape（或 profile 范围），正是为了编译期确定 kernel tile size 和内存布局。
- 动态 shape 支持（TRT dynamic shape）通过 optimization profile 近似，代价是多份 engine。

---

### 1.6 推理系统中调度（Scheduler）解决什么问题？

**【锚点】** 调度器解决"有限 GPU 资源 × 无限并发请求"的矛盾，最大化吞吐同时保证延迟。

**【答案】**

核心问题：

- **资源约束**：KV Cache 显存有限，不能无限并发
- **请求异构**：不同请求的 prompt 长度、生成长度差异极大
- **优化目标冲突**：高吞吐（大 batch）vs 低延迟（小 batch）

调度器决策：

- 哪些请求进入本轮 batch（waiting → running）
- KV Cache block 分配与回收
- 当显存不足时，抢占哪个请求（swap out 到 CPU 或 recompute）

**【深挖】**

- vLLM 默认策略：FCFS（先来先服务）+ 抢占时优先换出最新的请求（保住老请求减少重算）。

---

### 1.7 Iteration-level Schedule 是什么？解决什么问题？

**【锚点】** 每生成一个 token 就重新调度一次，新请求可在任意 token 步插入 batch。

**【答案】**

传统 static batching：一个 batch 从开始到全部请求结束才释放，短请求等长请求浪费资源。

Iteration-level（continuous batching）：

- 每个 decode step 结束后检查完成请求，立即从 waiting 队列补充新请求
- 本质：batch 是"动态集合"，每步成员可变

**效果**：GPU 利用率从 ~40% 提升到 ~80%+，TTFT 大幅降低。

**【深挖】**

- 实现约束：所有请求必须共享同一次 forward，要求 attention kernel 能处理不同长度序列（PagedAttention 的必要性）。

---

### 1.8 vLLM 的整体架构与请求流转路径？

**【锚点】** AsyncEngine → Scheduler → BlockManager → Worker → Sampler，KV Cache 用 PagedAttention 管理。

**【答案】**

```
Client
  ↓ HTTP (OpenAI API 兼容)
AsyncLLMEngine
  ↓ tokenize → SequenceGroup
Scheduler
  ├── waiting queue
  ├── running queue  
  └── swapped queue
  ↓ SchedulerOutputs（batch metadata + block table）
Worker（每卡一个进程）
  ↓ model.forward(input_ids, positions, kv_cache, attn_metadata)
Sampler
  ↓ next_token_ids
OutputProcessor
  ↓ detokenize → stream to client
```

BlockManager 维护 `block_table`：每个序列的逻辑 block → 物理 block 映射。

**【深挖】**

- vLLM v1（重构版）将 Engine 分为 `EngineCore`（调度+状态管理）和 `AsyncEngine`（异步接口），减少 Python GIL 瓶颈。

---

### 1.9 vLLM 请求被抢占后的处理机制？

**【锚点】** 抢占 = KV Cache 不足时驱逐请求，两种恢复方式：Swap（换出到 CPU）或 Recompute（直接丢弃重算）。

**【答案】**

- **Swap**：将 KV Cache blocks 拷贝到 CPU DRAM，请求进入 swapped queue；显存释放后换回继续。
    - 代价：PCIe 带宽（~32 GB/s），换出/换入延迟高
- **Recompute**：丢弃 KV Cache，请求退回 waiting queue，重新 Prefill。
    - 代价：重跑 Prefill（compute），但无 PCIe 传输

**选择策略**：vLLM 默认 recompute（更简单），实际部署中短 prompt 用 recompute 更快，长 prompt 用 swap 更合算。

**【深挖】**

- Prefix Cache 命中可大幅减少 recompute 代价：只需重算未命中部分。

---

### 1.10 vLLM 与 SGLang 的核心差异？

**【锚点】** vLLM 是通用推理服务，SGLang 在 RadixAttention + 结构化生成上有显著优势。

**【答案】**

|维度|vLLM|SGLang|
|---|---|---|
|KV Cache 复用|Prefix Cache（hash 匹配）|RadixAttention（Radix Tree，更细粒度）|
|结构化输出|基本支持|原生 FSM-guided decoding，更高效|
|调度架构|Python 调度器（GIL 瓶颈）|Zero-overhead scheduling（v0.4+）|
|多模态|完善|追赶中|
|生态|更广（插件、量化）|更快（尤其 batch inference）|

**【深挖】**

- RadixAttention：将所有请求的 KV Cache 组织成 Radix Tree，共同前缀自动共享，不需要显式 hash 对齐。

---

### 1.11 Continuous Batching vs Static Batching

**【锚点】** Static = 等全员到齐再发车；Continuous = 随时上下车，座位实时调整。

**【答案】**

- **Static Batching**：同一 batch 的所有请求必须等最长序列完成，短序列空转（padding）。
- **Continuous Batching**：每个 iteration 结束后动态调整 batch 成员，完成的请求立即离开，新请求立即加入。

吞吐提升原理：消除了"批内最长序列"对短序列的阻塞，GPU 算力持续被充分利用。

**【深挖】**

- 实现难点：attention 需要支持变长序列（varlength attention），PagedAttention 解决了这个问题。

## 2. Attention / Transformer

---

### 2.1 Self-Attention 完整公式推导

**【锚点】** Q 问问题，K 提供索引，V 提供内容，相似度加权聚合。

**【答案】**

输入序列 $X \in \mathbb{R}^{n \times d_{model}}$，投影：

$$Q = XW_Q, \quad K = XW_K, \quad V = XW_V$$

其中 $W_Q, W_K, W_V \in \mathbb{R}^{d_{model} \times d_k}$。

注意力分数：

$$A = \frac{QK^\top}{\sqrt{d_k}} \in \mathbb{R}^{n \times n}$$

归一化（因果掩码场景加 $-\infty$ mask 于未来位置）：

$$\hat{A} = \text{softmax}(A)$$

输出：

$$\text{Attention}(Q, K, V) = \hat{A} V \in \mathbb{R}^{n \times d_k}$$

**【深挖】**

- 计算复杂度：$O(n^2 d_k)$，瓶颈在 $QK^\top$ 的 $n^2$ 项。

---

### 2.2 为什么 Attention 要除以 $\sqrt{d_k}$？

**【锚点】** $d_k$ 维随机向量点积方差为 $d_k$，除以 $\sqrt{d_k}$ 将方差归一化为 1，防止 softmax 饱和。

**【答案】**

设 $q_i, k_j \sim \mathcal{N}(0, 1)$，独立同分布，则：

$$q_i \cdot k_j = \sum_{l=1}^{d_k} q_{il} k_{jl}$$

$$\mathbb{E}[q_i \cdot k_j] = 0, \quad \text{Var}[q_i \cdot k_j] = d_k$$

方差与 $d_k$ 成正比。$d_k$ 大时点积值域很大，softmax 输入极端，梯度趋近于 0（梯度消失）。

除以 $\sqrt{d_k}$ 后：

$$\text{Var}\left[\frac{q_i \cdot k_j}{\sqrt{d_k}}\right] = 1$$

**【深挖】**

- 推理时不需要梯度，但数值稳定性仍重要：极端 logit 导致 softmax 输出接近 one-hot，注意力退化为硬检索。

---

### 2.3 Softmax 为什么要减去 max？

**【锚点】** 数值稳定技巧，避免 $e^{x}$ 在 $x$ 很大时上溢出，结果数学等价。

**【答案】**

原始：$\text{softmax}(x_i) = \dfrac{e^{x_i}}{\sum_j e^{x_j}}$

当 $x_i = 1000$ 时，$e^{1000}$ 溢出（IEEE 754 FP16 最大约 $6.5 \times 10^4$）。

减去 $m = \max_j x_j$：

$$\text{softmax}(x_i) = \frac{e^{x_i - m}}{\sum_j e^{x_j - m}}$$

分子分母同除 $e^m$，结果不变；但 $x_i - m \leq 0$，$e^{x_i - m} \in (0, 1]$，不再溢出。

**【深挖】**

- Online softmax 在 FlashAttention 中的作用：分块时每块有局部 max，需要跨块修正，这正是 online softmax 的核心。

---

### 2.4 Online Softmax 的推导与实现

**【锚点】** 两遍扫描变一遍：维护运行 max 和运行 sum，每步修正历史 sum。

**【答案】**

标准 softmax 需要两遍扫描（第一遍求 max，第二遍求 sum）。Online softmax 合并为一遍：

维护状态 $(m_i, d_i)$，其中 $m_i = \max_{j \leq i} x_j$，$d_i = \sum_{j \leq i} e^{x_j - m_i}$。

处理第 $i+1$ 个元素 $x_{i+1}$，令 $m_{i+1} = \max(m_i, x_{i+1})$：

$$d_{i+1} = d_i \cdot e^{m_i - m_{i+1}} + e^{x_{i+1} - m_{i+1}}$$

修正因子 $e^{m_i - m_{i+1}}$：将历史 sum 重新对齐到新的 max。

最终 $\text{softmax}(x_j) = e^{x_j - m_n} / d_n$。

**【深挖】**

- FlashAttention 将序列分成 tile，每个 tile 独立计算 $(m, d)$，最后合并：正是 online softmax 的分块版本。

---

### 2.5 MHA / GQA / MQA / MLA 的差异

**【锚点】** 差异本质是 KV head 数量，MHA=全量，MQA=1，GQA=中间，MLA=压缩投影。

**【答案】**

设 $h$ 为 Q head 数，$d_h$ 为每 head 维度：

|方案|KV Head 数|KV Cache 大小|精度损失|
|---|---|---|---|
|**MHA**|$h$|$2 \cdot h \cdot d_h$ per token|无|
|**MQA**|$1$|$2 \cdot d_h$ per token|较大|
|**GQA**|$g$（$1 < g < h$）|$2 \cdot g \cdot d_h$ per token|中等|
|**MLA**|低秩压缩|$d_c \ll h \cdot d_h$ per token|极小|

**GQA**：$h$ 个 Q head 分成 $g$ 组，同组共享一对 KV head。

**MLA**（DeepSeek）：KV 通过低秩矩阵压缩到 $d_c$ 维潜空间存储，解码时上投影恢复，KV Cache 压缩比可达 $5\sim 13\times$。

**【深挖】**

- MLA 存储的是压缩后的 $c_{KV} \in \mathbb{R}^{d_c}$，而非完整 K、V；代价是解码时需要额外矩阵乘法上投影。

---

### 2.6 Pre-Norm vs Post-Norm

**【锚点】** Pre-Norm 训练更稳定（梯度不消失），Post-Norm 理论表达能力更强但难训。

**【答案】**

- **Post-Norm**（原始 Transformer）：$x' = \text{LayerNorm}(x + \text{Sublayer}(x))$
- **Pre-Norm**（GPT-2 / LLaMA）：$x' = x + \text{Sublayer}(\text{LayerNorm}(x))$

Pre-Norm 的残差路径 $x$ 不经过 LayerNorm，梯度可以直接反传，避免深层网络梯度消失。代价：训练收敛后性能略低于精心调参的 Post-Norm。

**【深挖】**

- RMSNorm（LLaMA 使用）是 LayerNorm 的简化版，去掉均值中心化，只保留方差归一化，计算更快。

---

### 2.7 Transformer 哪个模块计算量最大？

**【锚点】** 长序列时 Attention 是 $O(n^2)$ 瓶颈；短序列时 FFN（MLP）占大头。

**【答案】**

对于序列长度 $n$，模型维度 $d$，FFN 中间维度 $4d$：

- **Attention**：$QK^\top$ 计算量 $\approx 2n^2 d$ FLOP，随 $n$ 二次增长
- **FFN**：两次线性变换 $\approx 2 \times 2nd \times 4d = 16nd^2$ FLOP，随 $n$ 线性增长

临界点：$2n^2 d \approx 16nd^2 \Rightarrow n \approx 8d$

GPT-3 中 $d = 12288$，临界 $n \approx 98304$ tokens。实际推理序列通常远小于此，FFN 占更大比例。

**【深挖】**

- Decode 阶段（batch=1，n=1）：Attention 退化为向量-矩阵乘，FFN 仍是矩阵-向量乘，两者都 memory-bound，带宽是瓶颈。

## 3. KV Cache / 推理核心优化

---

### 3.1 KV Cache 的定义与显存计算公式

**【锚点】** 缓存已计算的 K、V，避免自回归时重复计算，代价是显存线性增长。

**【答案】**

自回归生成第 $t$ 步时，需要前 $t-1$ 步所有 token 的 K、V。若不缓存则需重算，时间复杂度 $O(n^2)$；缓存后每步只算新 token，时间复杂度 $O(n)$，代价是显存。

**显存计算**（MHA）：

$$M_{KV} = 2 \times n_{layers} \times h \times d_h \times L \times \text{bytes_per_element}$$

其中：$n_{layers}$ = 层数，$h$ = KV head 数，$d_h$ = head 维度，$L$ = 序列长度。

LLaMA-3-70B 示例（FP16，$n_{layers}=80$，$h=8$（GQA），$d_h=128$，$L=4096$）：

$$M_{KV} = 2 \times 80 \times 8 \times 128 \times 4096 \times 2 \approx 42 \text{ GB}$$

**【深挖】**

- FP8 量化 KV Cache 可减半显存，INT4 可减至 1/4，但需注意 outlier 处理。

---

### 3.2 PagedAttention 的设计动机与原理

**【锚点】** 借鉴操作系统虚拟内存分页，KV Cache 按固定大小 block 管理，消除碎片。

**【答案】**

**问题**：传统 KV Cache 预分配连续显存（按最大序列长度），导致：

- 内部碎片：短序列浪费预分配空间
- 外部碎片：无法合并空闲块
- 无法共享：相同前缀的不同请求各自持有独立 KV Cache

**PagedAttention 方案**：

- KV Cache 划分为固定大小的 **physical block**（每 block 存 $B$ 个 token 的所有层 KV）
- 每个序列维护 **block table**：逻辑 block 编号 → 物理 block 编号
- 物理 block 可不连续，类似操作系统页表
- 相同前缀可通过 Copy-on-Write 共享物理 block（Prefix Cache）

**【深挖】**

- Page size $B$ 的选择：太小则 block table 开销大、kernel launch 开销高；太大则内部碎片增多。实践中 vLLM 默认 $B=16$。

---

### 3.3 Chunked Prefill 的设计

**【锚点】** 将长 Prefill 拆成小 chunk，与 Decode 请求混合执行，平衡 TTFT 和 TPOT。

**【答案】**

**问题**：大 batch Prefill（如 8192 token prompt）占用整个 iteration，期间其他 Decode 请求的 TPOT 飙升。

**Chunked Prefill**：

- 将 Prefill 序列按固定 chunk size（如 512 token）分割
- 每个 iteration 只处理一个 chunk，剩余算力填充 Decode 请求
- Prefill 和 Decode 在同一 forward pass 中执行（mixed batch）

**效果**：

- TPOT 稳定（Decode 不被 Prefill 阻塞）
- GPU 利用率更高（Decode 填充 Prefill 的空闲算力）
- TTFT 略有延迟（Prefill 被拆分）

**【深挖】**

- 实现上需要 attention kernel 支持 mixed prefill-decode（不同请求有不同的序列状态），需要正确处理 causal mask。

---

### 3.4 PD 分离（Prefill/Decode 分离）原理

**【锚点】** Prefill compute-bound，Decode memory-bound，两种算力特性不同，分开部署最优。

**【答案】**

**瓶颈差异**：

|阶段|并行度|算术强度|瓶颈|
|---|---|---|---|
|Prefill|序列内 token 并行|高（GEMM 密集）|Compute|
|Decode|batch 间并行|低（逐 token）|Memory Bandwidth|

**PD 分离方案**：

- **Prefill 节点**：少量高算力 GPU（A100/H100），大 batch Prefill，完成后将 KV Cache 传输给 Decode 节点
- **Decode 节点**：多量 GPU，维持高 batch size，持续生成

KV Cache 传输带宽要求：以 LLaMA-3-70B、序列 4096 token 为例，单请求 KV Cache ~40 MB，需 RDMA（~200 Gbps = 25 GB/s）或 NVLink。

**【深挖】**

- NIXL（NVIDIA Inference Transfer Library）专为 PD 分离场景设计，支持异步 KV Cache 传输，避免 NCCL 的全局同步开销。

## 4. 推理优化方法论

---

### 4.1 如何判断推理瓶颈类型（Roofline 模型）

**【锚点】** 算术强度 $I = \text{FLOP} / \text{Bytes}$，与 Ridge Point 比较决定瓶颈类型。

**【答案】**

**Roofline 模型**：

$$\text{Attainable Performance} = \min\left(\text{Peak FLOPS},\ I \times \text{Peak Bandwidth}\right)$$

- **Ridge Point**：$I^* = \text{Peak FLOPS} / \text{Peak Bandwidth}$
- $I < I^*$：Memory-bound（带宽瓶颈）
- $I > I^*$：Compute-bound（算力瓶颈）

H100 SXM 示例：

- Peak FP16 FLOPS：$\approx 989$ TFLOPS（dense）
- Peak HBM Bandwidth：$\approx 3.35$ TB/s
- Ridge Point：$\approx 295$ FLOP/Byte

Decode 阶段（batch=1）：GEMM $m=1$，$I \approx 2$ FLOP/Byte，远低于 Ridge Point → Memory-bound。

**【深挖】**

- 实际用 `ncu`（Nsight Compute）的 Roofline Chart 分析具体 kernel，`nsys` 分析系统级瓶颈。

---

### 4.2 Speculative Decoding 原理

**【锚点】** 小模型猜多步，大模型一次验证，验证并行而非逐步串行，吞吐提升而延迟不增。

**【答案】**

**标准解码**：每步调用大模型（target model）生成 1 token，串行，延迟高。

**投机解码**：

1. Draft model（小模型）自回归生成 $\gamma$ 个 draft token：$\tilde{x}_1, \ldots, \tilde{x}_\gamma$
2. Target model **并行**验证所有 $\gamma$ token（一次 Prefill-like forward）
3. 接受/拒绝：
    - 若 $p_{target}(\tilde{x}_t) \geq p_{draft}(\tilde{x}_t)$：接受
    - 否则以概率 $\min(1, p_{target}/p_{draft})$ 接受（rejection sampling，保证输出分布等价）
4. 第一个被拒绝的位置之后重新采样

**加速比**：期望接受长度 $\mathbb{E}[\tau] = \gamma \alpha / (1 - \alpha^\gamma)$（$\alpha$ 为单 token 接受率），实际加速 $2\sim 3\times$。

**【深挖】**

- EAGLE-3（Extrapolation Algorithm for Greater Language-model Efficiency）：用 feature-level 预测代替 token-level 预测，接受率更高（$\alpha \approx 0.8+$）。

## 5. FlashAttention / 高效 Attention

---

### 5.1 FlashAttention 核心思想与 IO-Aware 设计

**【锚点】** 不把 $n \times n$ attention matrix 写回 HBM，在 SRAM 内分块完成 softmax + 加权求和，IO 复杂度从 $O(n^2)$ 降至 $O(n)$。

**【答案】**

**瓶颈分析**：标准 Attention 的 IO：

- 读 Q、K、V：$O(nd)$
- 写 attention matrix $S = QK^\top$：$O(n^2)$ ← 主要瓶颈
- 读 $S$ 做 softmax：$O(n^2)$
- 读 $\hat{A}$ 和 V 做加权：$O(n^2 + nd)$

Total IO：$O(n^2)$，当 $n$ 大时 $n^2 \gg nd$。

**FlashAttention**：将 Q、K、V 分块加载到 SRAM（L2 / Shared Memory），在 SRAM 内用 online softmax 完成计算，只写最终输出 $O$。

IO 复杂度：$O(nd)$（只读写 Q、K、V、O），$n^2$ 的中间矩阵完全不落 HBM。

**【深挖】**

- 反向传播：不存储 attention matrix，需要重计算（recomputation），用 $O$ 和 softmax 统计量 $(m, l)$ 恢复，额外 FLOP 换 IO 节省。

---

### 5.2 FlashAttention V1 / V2 / V3 差异

**【答案】**

|版本|核心改进|GPU 利用率|
|---|---|---|
|FA v1 (2022)|IO-aware 分块，online softmax|~30% A100 MFU|
|FA v2 (2023)|减少非矩阵乘 FLOP，Q 外循环 K/V 内循环（更好 parallelism），warp 分工优化|~70% A100 MFU|
|FA v3 (2024)|H100 专属：Tensor Core 异步流水（WGMMA + TMA），FP8 支持，ping-pong pipeline|~75% H100 MFU|

**【深挖】**

- FA v2 的关键改变：将 Q 放外循环，K/V 放内循环，使得同一 warp 处理的 Q 块不需要在 warp 间通信，消除了 FA v1 的 warp 间 reduce 开销。

## 6. 量化（Quantization）

---

### 6.1 PTQ vs QAT

**【锚点】** PTQ 训练后直接量化（快但精度低），QAT 训练时模拟量化误差（慢但精度高）。

**【答案】**

||PTQ|QAT|
|---|---|---|
|时机|训练完成后|训练/微调中|
|数据需求|少量校准数据|完整训练数据|
|计算成本|低（小时级）|高（天级）|
|精度|INT8 可接受，INT4 有损|INT4 可接受|
|典型方案|GPTQ、AWQ、SmoothQuant|QLoRA（近似 QAT）|

**【深挖】**

- LLM 体量大，QAT 成本极高，主流方案以 PTQ 为主，配合 groupwise 量化和误差补偿。

---

### 6.2 量化公式与流程

**【锚点】** $x_q = \text{clamp}(\text{round}(x/s), -2^{b-1}, 2^{b-1}-1)$，反量化 $\hat{x} = x_q \cdot s$。

**【答案】**

对称量化（zero-point = 0）：

$$s = \frac{\max(|x|)}{2^{b-1} - 1}, \quad x_q = \text{round}!\left(\frac{x}{s}\right)$$

计算流程（weight-only INT4 推理）：

1. 存储：权重 INT4 存储（显存减半）
2. 加载：从 HBM 读 INT4 权重（带宽占用减半）
3. 解量化：INT4 → FP16（在寄存器中，无 HBM IO）
4. 计算：FP16 GEMM
5. 输出：FP16 activation

**【深挖】**

- Group-wise 量化：每 $g$（如 128）个权重共享一个 scale，精度显著优于 per-tensor，代价是额外存储 scale（通常可忽略）。

---

### 6.3 SmoothQuant / GPTQ / AWQ 原理

**【答案】**

**SmoothQuant**（activation 量化难点：outlier）：

- 将 activation 的量化难度迁移给 weight：$Y = (X \cdot \text{diag}(s)^{-1}) \cdot (\text{diag}(s) \cdot W)$
- $s_j = \max(|X_j|)^\alpha / \max(|W_j|)^{1-\alpha}$，$\alpha$ 控制迁移程度
- 结果：activation 更平滑（易量化），weight 稍有 outlier（但 weight 更耐量化）

**GPTQ**（weight-only，layer-by-layer）：

- 基于 OBQ（Optimal Brain Quantization），用二阶 Hessian 信息最小化量化误差
- 逐列量化权重，每量化一列立即用残差更新未量化列
- Lazy Batch-Updates + Cholesky 分解提升数值稳定性和效率

**AWQ**（Activation-aware Weight Quantization）：

- 核心观察：$\approx 1%$ 的权重 channel（对应 activation outlier 的 channel）对精度贡献极大
- 对这些 salient channel 乘以 scale 保护精度（等效于增大量化分辨率），其余 channel 正常量化

**【深挖】**

- AWQ 不需要反向传播，搜索 per-channel scale 仅需少量校准数据，速度快于 GPTQ。

---

## 7. CUDA / GPU 架构

---

### 7.1 CUDA 编程模型

**【锚点】** Thread < Warp(32) < Block < Grid，Block 内共享 Shared Memory，Warp 是执行单位。

**【答案】**

```
Grid
└── Block (threadIdx.x/y/z)
    └── Warp (32 threads，SIMT 执行)
        └── Thread
```

- **SM（Streaming Multiprocessor）**：硬件执行单元，一个 SM 同时驻留多个 Block（受 shared memory / register 限制）
- **Warp**：32 个 thread 同步执行同一指令（SIMT），warp 内分支导致 divergence
- **Shared Memory**：Block 内所有 thread 共享，延迟 ~4 cycle（对比 HBM ~800 cycle）

**【深挖】**

- H100 每 SM：228 KB L1/Shared Memory，256K 寄存器，最多 32 warp（1024 thread）驻留。

---

### 7.2 Shared Memory Bank Conflict

**【锚点】** 32 路 bank，同 warp 内多个 thread 访问同一 bank 不同地址 → 串行化，性能下降。

**【答案】**

Shared Memory 分 32 个 bank，每 bank 宽度 4 字节。Bank 编号 = 地址 / 4 % 32。

**无 conflict**：warp 内 32 个 thread 访问 32 个不同 bank（完美 stride-1 访问）。

**2-way conflict**：2 个 thread 访问同一 bank 的不同地址，该 bank 访问串行，吞吐减半。

**避免方法**：

- Padding：在每行末尾填充 1 个 float（改变列的 bank 映射）
- 调整访问 layout（transpose 时 tile 设计）

**【深挖】**

- 广播（broadcast）不是 conflict：多个 thread 访问同一 bank 的**同一地址**，硬件广播，无性能损失。

---

### 7.3 Global Memory Coalescing

**【锚点】** 同 warp 的 32 个 thread 访问连续对齐的 128 字节 → 一次 memory transaction，否则多次。

**【答案】**

HBM 访问以 cache line（128 字节 = 32 个 float4）为单位。

**Coalesced（理想）**：thread $i$ 访问地址 $base + i \times 4$，32 个 thread 覆盖 128 字节 → 1 transaction。

**Non-coalesced（糟糕）**：thread $i$ 访问地址 $base + i \times 128$（stride-128），每个 thread 单独 1 transaction → 32 transactions，带宽利用率 $1/32$。

**【深挖】**

- Matrix transpose kernel 优化：先 coalesced 读入 shared memory（tile 存储），在 shared memory 内 transpose，再 coalesced 写出。

---

### 7.4 CUDA Graph

**【锚点】** 将一系列 kernel launch 记录为图，一次提交执行，消除 CPU launch overhead。

**【答案】**

问题：每次 kernel launch 需要 CPU → GPU 命令提交，延迟 ~5-10 μs，大量小 kernel 时 CPU 成为瓶颈。

CUDA Graph：

1. **录制阶段**：`cudaStreamBeginCapture` → 执行所有 kernel → `cudaStreamEndCapture`，得到 `cudaGraph_t`
2. **实例化**：`cudaGraphInstantiate` 生成 `cudaGraphExec_t`
3. **执行**：`cudaGraphLaunch`，一次 CPU 调用触发整个图

**优化效果**：消除逐 kernel 的 CPU launch overhead，适合固定计算图的推理场景（batch size / sequence length 不变时）。

**【深挖】**

- 动态 shape 下 CUDA Graph 需要 "graph capture with dynamic parameters" 或使用多份 graph，实现复杂。
- vLLM 通过 `CUDAGraphRunner` 对固定 batch size 使用 CUDA Graph，其他 batch size 回退到 eager 执行。

---

## 8. CUDA Kernel 优化

---

### 8.1 GEMM 优化手段

**【锚点】** 三级 tiling（Global→Shared→Register），向量化加载，隐藏 memory latency。

**【答案】**

GEMM $C = AB$，$A \in \mathbb{R}^{M \times K}$，$B \in \mathbb{R}^{K \times N}$：

```
Level 1: Thread Block Tile (BM × BN × BK)
  - 每个 Block 负责输出 C 的 BM×BN 子块
  - A、B 的 BM×BK 和 BK×BN 子块加载到 Shared Memory

Level 2: Warp Tile (WM × WN × WK)
  - 每个 Warp 处理 WM×WN 输出
  - Shared Memory → Register File

Level 3: Thread Tile (TM × TN)
  - 每个 Thread 计算 TM×TN 输出，寄存器累加
```

关键技术：

- **Double buffering**：计算当前 tile 的同时，异步预加载下一个 tile（hide memory latency）
- **向量化加载**：`float4` 一次加载 16 字节，提升 HBM 带宽利用率
- **Tensor Core**（H100）：`wmma` / `mma` 指令，FP16 矩阵乘吞吐提升 8-16×

**【深挖】**

- CUTLASS 实现了上述所有优化，并提供 epilogue fusion（bias add、activation 融合在同一 kernel）。

---

### 8.2 Kernel Fusion

**【锚点】** 将多个算子合并为一个 kernel，消除中间结果写 HBM 的 IO，适合 memory-bound 算子序列。

**【答案】**

不融合：

```
Kernel 1: LayerNorm → 写结果到 HBM
Kernel 2: 读 HBM → Linear → 写结果到 HBM  
Kernel 3: 读 HBM → GELU → 写结果到 HBM
```

融合后：

```
Kernel 1: 读输入 → LayerNorm → Linear → GELU → 写输出
中间结果驻留在寄存器/Shared Memory，不落 HBM
```

**适合融合的算子**：element-wise（ReLU、GELU、scale）、LayerNorm、bias add、softmax。

**不适合融合**：GEMM（compute-bound，融合反而干扰 tile 策略）。

**【深挖】**

- Triton 使得 kernel fusion 可以用 Python 描述，编译器自动处理 shared memory / tiling，降低开发门槛。

---

### 8.3 Warp-level Primitive（Shuffle）

**【锚点】** Warp 内 thread 直接交换寄存器数据，无需 Shared Memory，延迟极低（~2 cycle）。

**【答案】**

`__shfl_sync(mask, val, srcLane)`：从 `srcLane` 号 thread 的寄存器广播 `val` 到 mask 指定的所有 thread。

Warp reduce 示例（求 warp 内 32 个值的和）：

```cpp
float val = ...; // 每个 thread 持有一个值
for (int offset = 16; offset > 0; offset >>= 1) {
    val += __shfl_down_sync(0xffffffff, val, offset);
}
// thread 0 中 val = 32 个值的和
```

对比 Shared Memory reduce：

- Shuffle：~2 cycle per step，无 bank conflict 风险
- Shared Memory：~4 cycle + 同步开销

**【深挖】**

- 跨 warp 的 reduce 仍需 Shared Memory 或 atomic，shuffle 只在 warp 内有效。

## 9. 分布式 / 通信

---

### 9.1 常见通信原语

**【锚点】** AllReduce = ReduceScatter + AllGather，是 TP 的核心原语。

**【答案】**

|原语|含义|典型用途|
|---|---|---|
|**Broadcast**|1 → N，主节点数据发给所有节点|参数初始化|
|**Reduce**|N → 1，所有节点数据聚合到主节点|梯度聚合（非 ring）|
|**AllReduce**|N → N，所有节点获得全局聚合结果|TP 中 attention/FFN 输出求和|
|**ReduceScatter**|N → N，结果分片分配给各节点|ZeRO-2/3 梯度分片|
|**AllGather**|N → N，各节点分片 → 每节点获完整数据|ZeRO 参数还原，TP|

**AllReduce = ReduceScatter + AllGather**（Ring AllReduce 实现）：

- 两阶段各需 $2 \times \dfrac{N-1}{N} \times \text{data\_size}$ 数据传输量

**【深挖】**

- TP（Tensor Parallelism）中，每层 FFN 需要 2 次 AllReduce（列并行+行并行），通信量 $= 2 \times bsh \times 2$ bytes（b=batch，s=seq，h=hidden）。

---

### 9.2 TP / PP / DP / EP 原理

**【答案】**

|并行策略|切分维度|通信|适用场景|
|---|---|---|---|
|**DP（数据并行）**|batch|AllReduce 梯度|训练为主，推理多副本|
|**TP（张量并行）**|权重矩阵列/行|AllReduce（每层）|单机多卡，低延迟推理|
|**PP（流水线并行）**|模型层|P2P（层间激活）|超大模型，跨机|
|**EP（专家并行）**|MoE 专家|AlltoAll|MoE 模型推理|

**TP 原理（Megatron 方案）**：

FFN 第一层列并行切分：$Y = XW_1$，将 $W_1$ 按列切分到 $p$ 卡，各卡独立计算，激活函数后行并行第二层，最后 AllReduce。

**【深挖】**

- 推理中 TP 的通信延迟是瓶颈，因此 TP 通常限制在 NVLink 互联的节点内（NVLink ~900 GB/s vs IB ~400 Gbps）。

## 10. 系统 / 工程

---

### 10.1 显存组成与 OOM 排查

**【锚点】** 显存 = 权重 + KV Cache + Activations + CUDA Context，OOM 先看哪项超预期。

**【答案】**

显存组成（推理时）：

|部分|计算|典型占比|
|---|---|---|
|**模型权重**|$\text{params} \times \text{bytes}$|LLaMA-70B FP16 ≈ 140 GB|
|**KV Cache**|$2 \times L \times h \times d_h \times n_{seq} \times \text{bytes}$|可达数十 GB|
|**Activations**|与 batch size、chunk size 相关|较小（GB 级）|
|**CUDA 上下文**|Driver + runtime|~1 GB|
|**临时 buffer**|Kernel workspace|可忽略|

**OOM 排查步骤**：

1. `nvidia-smi` 确认显存用量
2. 检查权重加载是否超预期（量化是否生效）
3. 检查 KV Cache 分配（vLLM `gpu_memory_utilization` 参数）
4. 检查 batch size × seq_len 的 activation 峰值
5. 检查是否有显存泄漏（`torch.cuda.memory_snapshot()`）

**【深挖】**

- vLLM 启动时会 profiling 一次 dummy forward 来测量权重 + activation 占用，剩余显存全部分配给 KV Cache（`BlockManager`）。

---

### 10.2 Profiling 工具与设计

**【锚点】** `nsys` 看系统级时间线（kernel 调度、通信），`ncu` 看单 kernel 硬件指标（带宽利用率、occupancy）。

**【答案】**

|工具|粒度|典型用途|
|---|---|---|
|`nsys profile`|系统级（μs）|kernel launch 时间线、NCCL 通信、CPU-GPU overlap|
|`ncu`|kernel 级（cycle）|内存带宽利用率、Roofline、warp occupancy|
|`torch.profiler`|Python 级|PyTorch op 耗时，方便快速定位|
|`DCGM`|设备级|GPU 利用率、功耗、NVLink 流量监控|

**Profiling 插桩影响**：

- `nsys` overhead：~1-5%（事件记录）
- `ncu` overhead：极高（逐 cycle 硬件计数器），生产不可用，仅用于离线分析

**【深挖】**

- `ncu --set roofline` 直接输出 Roofline chart，是判断 memory/compute bound 的标准工作流。

## 11. C++ / 基础

---

### 11.1 虚函数与 vtable

**【锚点】** 每个含虚函数的类有一张 vtable，对象头部有 vptr 指向它，虚调用 = 两次间接寻址。

**【答案】**

```cpp
class Base {
    void* vptr;           // 编译器插入，指向 Base::vtable
    virtual void foo();   // vtable[0] = &Base::foo
};
class Derived : public Base {
    // vptr 指向 Derived::vtable
    void foo() override;  // Derived::vtable[0] = &Derived::foo
};
```

虚函数调用汇编（伪）：

```
mov rax, [rdi]        ; 加载 vptr（对象首地址）
call [rax + offset]   ; 跳转到 vtable 对应槽
```

代价：2 次内存间接（vptr + vtable 槽），无法内联，分支预测失效。

**【深挖】**

- CRTP（编译期多态）：`template<class Derived> class Base { Derived& self(); }`，虚函数开销为零，但无法运行时多态。

---

### 11.2 智能指针

**【锚点】** `unique_ptr` 独占，`shared_ptr` 引用计数，`weak_ptr` 打破循环引用。

**【答案】**

```cpp
// unique_ptr：独占所有权，移动语义
auto p = std::make_unique<Foo>();
auto q = std::move(p); // p 变为 nullptr

// shared_ptr：引用计数（原子操作），堆上 control block
auto sp1 = std::make_shared<Foo>(); // 一次分配（对象+control block）
auto sp2 = sp1; // ref_count = 2

// weak_ptr：不增加 ref_count，避免循环引用
std::weak_ptr<Foo> wp = sp1;
if (auto locked = wp.lock()) { /* use locked */ }
```

性能注意：

- `shared_ptr` 的 ref_count 操作是原子 fetch_add，多线程频繁拷贝有竞争开销
- 推理框架中 tensor 生命周期管理应优先 `unique_ptr` + 显式 transfer

---

### 11.3 std::move 与右值引用

**【锚点】** `move` 不移动数据，只是 static_cast 到右值引用，触发移动构造/赋值，避免深拷贝。

**【答案】**

```cpp
std::vector<int> a = {1, 2, 3};
std::vector<int> b = std::move(a); 
// a 的内部指针转移给 b，a 变为空向量
// 没有元素拷贝，O(1) vs O(n)
```

移动语义实现：

```cpp
class Buffer {
    float* data_;
    Buffer(Buffer&& other) noexcept 
        : data_(other.data_) { other.data_ = nullptr; }
};
```

**【深挖】**

- `noexcept` 对移动构造/赋值极为重要：`std::vector` 扩容时只有 `noexcept` 的移动构造才会被使用，否则退化为拷贝。

## 12. 模型 / 算法

### 12.1 LoRA 原理

**【锚点】** 权重更新矩阵 $\Delta W = AB$（低秩分解），只训练 $A$、$B$，参数量从 $d^2$ 降至 $2dr$。

**【答案】**

原始权重 $W_0 \in \mathbb{R}^{d \times d}$，冻结。引入可训练参数：

$$\Delta W = BA, \quad B \in \mathbb{R}^{d \times r},\ A \in \mathbb{R}^{r \times d},\ r \ll d$$

前向传播：

$$h = W_0 x + \Delta W x = W_0 x + BAx$$

初始化：$A \sim \mathcal{N}(0, \sigma^2)$，$B = 0$（保证训练初始时 $\Delta W = 0$）。

参数量对比：$W_0$ 有 $d^2$ 参数，$A+B$ 有 $2dr$ 参数，$r=8, d=4096$ 时压缩比 $\approx 512\times$。

**推理部署**：合并 $W = W_0 + BA$，无额外推理开销。

**【深挖】**

- QLoRA：以 NF4（4-bit）量化冻结基础模型，LoRA adapter 仍用 BF16，大幅降低显存需求，近似实现 full fine-tuning 效果。

### 12.2 MoE 路由机制与负载均衡

**【锚点】** TopK 路由选激活专家，负载不均导致专家空转，负载均衡损失 $L_{balance}$ 惩罚分布偏斜。

**【答案】**

MoE FFN：每个 token $x$ 经 Router 选 $K$ 个专家（$K \ll N$）：

$$\text{Router}(x) = \text{softmax}(W_g x)$$

$$\text{TopK indices} = \text{argtop}_K(\text{Router}(x))$$

$$\text{output} = \sum_{i \in \text{TopK}} g_i \cdot E_i(x)$$

其中 $g_i$ 为 router 分数（重新 softmax 归一化）。

**负载均衡损失**（Switch Transformer）：

$$L_{balance} = N \cdot \sum_{i=1}^{N} f_i \cdot P_i$$

$f_i$ = 专家 $i$ 处理的 token 比例，$P_i$ = router 分配给专家 $i$ 的平均概率。$f_i P_i$ 乘积最小化 → 均匀分布。

**【深挖】**

- Expert Parallelism（EP）：不同 GPU 持有不同专家，token 通过 AlltoAll 路由到对应 GPU，通信量 $\propto K \times \text{batch tokens}$。
