## 一个 CUDA Kernel 的性能瓶颈如何定位？
答：
1. 使用 Nsight Systems 查看端到端时间线，判断是否存在 CPU 调度开销、Kernel Launch 过多、Memcpy、Stream 空闲或同步等待。
2. 使用 Nsight Compute 分析关键 Kernel，查看 SM 吞吐率、DRAM/L2 吞吐率、Warp Stall、寄存器、Shared Memory 和 Occupancy。
3. 根据 Roofline 判断属于 Compute-bound 还是 Memory-bound。
4. 针对瓶颈调整 Tile、数据复用、访存合并、并行度或融合策略。
5. 用相同 Shape、数据类型、输入和测试条件复测延迟及正确性。

关键点：不能看到 GPU 利用率低就直接认定是访存瓶颈，也不能仅凭 Occupancy 高低判断性能好坏。

## 介绍 roofline
答：**实测算术强度 $I_{\text{actual}}$**

$$I_{\text{actual}} = \frac{\text{实际执行 FLOPs（FMA 指令数} \times 2\text{）}}{\text{实际 HBM 访问字节数}}$$
**计算 Roofline 脊点 $I^*$**

$$I^* = \frac{P_{\text{peak}}}{BW_{\text{HBM}}}$$

以 H100 SXM5 为例（FP16，非稀疏模式）：

$$I^*_{\text{H100}} = \frac{1979\ \text{TFLOPS}}{3.35\ \text{TB/s}} \approx 591\ \text{FLOP/Byte}$$

## 怎么解决 compute-bound？
如果计算单元利用率已经较高，则重点考虑 SIMD/SIMT 向量化、增加 ILP、优化线程映射、使用硬件矩阵乘单元、减少 instruction overhead，以及选择更适合硬件的计算精度。

## 怎么解决 memory-bound？
如果 profiling 发现 Arithmetic Intensity 较低、带宽利用率高而计算单元利用率低，我会优先优化访存，包括连续访问、coalescing、cache reuse、tiling、减少 global memory traffic、避免重复加载，以及必要时进行 operator fusion。

## CPU 和 GPU 在优化上的异同
CPU 和 GPU 优化的共同点是都要先通过 Profiling 定位瓶颈，再针对计算、访存、并行度和同步开销进行优化；

区别主要来自硬件架构，CPU 是少量强计算核心，更关注 Cache Locality、SIMD、Branch Prediction、Instruction-Level Parallelism 和线程同步，例如通过 Cache Blocking、数据布局和 AVX 向量化提高性能；

GPU 是大量并行计算单元，更关注 Thread/Block/Warp 的并行映射、Global Memory Coalescing、Shared Memory 数据复用、Register Pressure 和 Occupancy，例如通过 Tiling、Shared Memory、Warp-level Optimization 和 Kernel Fusion 提高吞吐。

因此 CPU 优化更偏向降低单线程延迟和提高 Cache/指令执行效率，GPU 优化更偏向提高大规模并行吞吐和隐藏 Memory Latency。

## 介绍SIMT和SIMD
SIMD（Single Instruction Multiple Data）和 SIMT（Single Instruction Multiple Threads）都是通过并行执行提高吞吐的方式，核心思想都是让一条指令同时处理多个数据，但执行模型不同：

SIMD 通常是 CPU 的向量化机制，一条向量指令作用于一个线程中的多个数据，例如 AVX2 的 256 bit 寄存器可以同时处理 8 个 FP32；

SIMT 是 GPU CUDA 的核心执行模型，一个 Warp 通常包含 32 个 Thread，线程各自拥有独立的寄存器和执行上下文，但硬件以 Warp 为单位执行相同的指令，因此可以理解为“多个线程协同执行同一条指令”。

两者的主要区别是 SIMD 强调“一个线程处理多个数据”，SIMT 强调“多个线程处理多个数据”；
当 SIMD/SIMT 中出现分支时，SIMD 通常需要通过 Mask 控制不同 Lane，GPU 的 SIMT 则会发生 Warp Divergence，同一个 Warp 中不同线程走不同分支时需要串行执行不同路径，因此都会受到分支不一致带来的性能影响。

## 为什么访问 Cache 比 DRAM 快？

## GPU 利用率很高，为什么性能仍然差？
答：GPU 利用率高不代表计算效率高，需要结合具体性能指标分析。GPU 利用率通常反映 GPU 是否处于忙碌状态，但不代表计算单元、显存带宽或 Tensor Core 得到了充分利用。

常见原因有四类：
第一，计算效率低，例如线程分支发散、Occupancy 低、指令依赖导致流水线停顿；
第二，访存效率低，例如非合并访存、Cache 命中率低、内存访问延迟高；
第三，资源竞争，例如寄存器或 Shared Memory 占用过高，限制了并发执行的 Warp 数量；
第四，执行效率低，例如 Kernel 数量过多、同步开销大，或者大量计算没有产生有效结果。

排查时，我会结合 Profiling 工具分析 SM 利用率、Tensor Core 活跃度、显存带宽、Occupancy、Warp Stall 和 Kernel 耗时，再根据瓶颈优化。例如，显存带宽接近峰值时优先优化访存与数据复用；计算单元忙但有效吞吐低时，检查指令效率、Warp 调度和流水线利用率；如果 Kernel 很短但调用频繁，则考虑 Kernel Fusion 和减少 Launch 开销。

面试总结：GPU 利用率高只说明设备比较忙，不代表硬件资源被高效利用。真正需要优化的是有效计算吞吐量、访存效率和端到端执行效率，而不是单纯追求 GPU 利用率达到 100%。

## 为什么增加 Shared Memory 使用量后，Kernel 可能变慢？
答：
Shared Memory 可以提升数据复用，但每个 Block 使用的 Shared Memory 增加后，一个 SM 能同时驻留的 Block 数量可能下降；如果寄存器占用也很高，活跃 Warp 数量会进一步受到限制，降低隐藏访存延迟的能力。此外，数据搬运、同步和 Bank Conflict 也可能抵消复用收益。

## 何时应该直接使用 L1/L2 Cache？
答：
**L2：**
1. **关键数据需要跨 Kernel 持久驻留**
   有多个 Kernel 顺序执行，且都反复访问同一块较小的核心数据集（比如矩阵乘法的常量块、迭代求解器的系数矩阵），默认的 L2 替换策略可能会在中间步骤把它挤出。此时应使用 **L2 Persistence** 机制（通过 `cudaAccessPolicyWindow` 或 PTX 的 `evict_last` 提示），将这块内存标记为“持久”，让硬件优先保留它。
2. **流式数据避免污染 L2**
   读一次就不再用”的数据，用 `cudaAccessPropertyStreaming` 或 PTX 的 `evict_first` 提示，让这些数据“快进快出”。
3. **显式预取以隐藏延迟**
   当 Kernel 需要访问一块已知地址、但硬件预取器可能无法及时识别的数据时，可以使用 PTX 的 `prefetch_size` 限定符（如 `L2::256B`）提前把数据拉进 L2，用计算时间掩盖访存延迟。

**L1：**
1. **使用 Shared Memory**：
   与L1共用同一片SRAM（静态随机存取存储），注意显式同步和bank冲突。
2. **只读数据强制走 L1/纹理路径**：
   如果数据在整个 Kernel 生命周期内**只读**，使用 `__ldg()` 或 `ld.global.nc` 可以让数据通过 L1/纹理缓存路径，比如： kernel 里同时有大量普通全局访问和只读访问，只读数据走独立路径，**不会去挤占普通 L1 的容量和带宽**。还能够被复用。
3. **绕过 L1 缓存**
   对于“写一次就不再读”或“流式访问”的数据，让它们经过 L1 是浪费。CUDA 提供了缓存提示（如 `__ldcg()` 或 PTX 的 `L1::no_allocate`）来限制 L1 缓存。Volta架构以后已经默认直写了。
   
## \_\_ldg 伪同步
答：
\_\_ldg（Load Global via Texture/Read-Only path）强制数据走只读数据缓存。这条路径的特点是：
- 非一致性：它假设数据在整个 kernel 生命周期内不会被写入，因此不需要监听写操作来维护一致性。
- 低开销：因为跳过了复杂的相干性检查，硬件可以更高效地预取和缓存数据

虽然 `__ldg` 本质上仍是**同步加载指令**，**允许指令级并行（ILP）**：由于 `__ldg` 告诉编译器“这块数据不会被改”，编译器敢于将后续不依赖于该数据的计算指令**调度到加载指令之前或之间执行**。这就形成了一种局部的重叠：在等待 `__ldg` 返回数据的同时，SM 可以继续执行其他独立的算术运算。

## 如何选择 Warp 数和 Pipeline Stage？
答：
两者核心矛盾在于：**Warp 数提升并行度（TLP）来隐藏延迟，而 Pipeline Stage 通过增加在途数据量（ILP）来隐藏延迟，但两者都会争抢同一份稀缺资源——Shared Memory 和寄存器。**

**warp：** 
	**先看硬性约束**：保证每个 SM 上有足够多的活跃 warp，来隐藏算术延迟，内存密集型 kernel，则需要更多 Warp。
	**资源：** 考虑Shared Memory 和 寄存器用量。

**Pipeline Stage：**
	**先算 Shared Memory 预算**
	**stage 数量调整：** 
	- **内存密集型 kernel**（如大矩阵乘、卷积）：访存延迟是主要矛盾。通常需要 **3 到 5 stages** 才能让内存总线充分运转。
	- **计算密集型 kernel**：计算本身足够长，能自然掩盖部分访存延迟。此时过多的 stages 只会浪费 Shared Memory，**2 到 3 stages** 往往就足够了。

相互制约。

## 算子融合什么时候有收益，什么时候没有？
答：
当多个连续算子之间存在中间张量写入和读取、额外 Kernel Launch 开销时，融合可能减少显存流量和启动次数；但融合也可能增加寄存器压力、Shared Memory 占用、指令数量及代码复杂度，甚至降低 Occupancy。

## FlashDecoding：FlashAttention Decode 阶段暴露的是并行度瓶颈，怎么优化
答：
核心思路是**改变并行化的维度**：既然 Query 序列长度只有 1，无法提供足够的并行块，那就沿着 **KV 序列长度维度进行切分（Split-K）**，把原本串行处理的 KV 缓存拆成多份，交给不同的 CTA 并行处理。
**切分数量需要动态选择。**
**合并阶段的同步开销是主要代价。** 每个 split 产生独立的 `(m, l, o)` 部分结果，需要用在线 softmax 的合并公式重新缩放后求和[](https://docs.rs/baracuda-kernels/latest/baracuda_kernels/attention/flash_decoding/#main-content#1)[](https://huggingface.co/datasets/Infatoshi/kernelbench-hard-traces/raw/main/20260613_055815_zai-claude_glm-5.2_03_paged_attention.jsonl#26)。合并 kernel 本身很小，但多一次 kernel 启动和同步。可考虑把并行计算和 reduction 放进同一个 kernel launch 来消除这个开销。

## 如何将一个 CUDA 算子迁移到昇腾或海光 DCU？
答：
### 思路
**第一步：资产盘点与可行性评估**
- 算子清单化：列出所有待迁移算子，标注类型、使用的 CUDA 特性、依赖的库。
- 目标平台能力比对：逐项确认共享内存、Warp 原语、数学库、精度支持等。
- 划定迁移边界：明确哪些必须迁移、哪些可用平台库替代、哪些可 CPU 回退。
- 产出《算子迁移评估表》，明确每个算子的迁移路径和预估工作量。

**第二步：选择迁移策略**
- 源码转换工具：适合手写 CUDA C++，速度快但覆盖率有限、性能有损。
- 生态兼容层：适合 PyTorch 自定义算子，改动小但受适配层成熟度限制。
- 跨平台语言重写：适合核心算子，自主可控但学习成本高。
- 调用目标平台库：适合标准算子，性能最优但仅覆盖标准逻辑。
- CPU 回退：适合非热点算子，零成本但性能差。
- 推荐组合：标准算子用平台库 → 框架层用兼容层 → 手写算子先试转换工具 → 效果差的用跨平台语言重写。

**第三步：执行迁移与适配**
- 内存模型适配：替换内存分配/拷贝 API，注意对齐和统一内存支持。
- 线程组织适配：Warp/Wavefront 尺寸差异（32 vs 64）、Block/Grid 限制变化。
- 计算原语适配：Warp Shuffle、原子操作、Tensor Core 指令、数学函数均需逐一核对。
- 同步与通信适配：`__syncthreads()`、Stream、Event、多卡通信库替换。
- 编译与构建适配：编译器切换、CMake/Makefile 重写、编译选项调整。

**第四步：正确性与性能验证**
- 正确性验证：建立 GPU 数值基准，逐层比对，设定误差阈值，覆盖边界用例。
- 性能验证：端到端耗时、算子级 Profiling、算力利用率、接受合理性能折损。
- 回归测试：建立自动化测试套件，防止后续更新导致回退。

### 核心注意事项（避坑指南）

1. **不要假设“语法通了就能跑对”**：自动转换只保证编译通过，语义正确性必须自己验证。
2. **精度问题是隐性杀手**：浮点运算顺序、舍入方式、快速数学函数均可能引入误差，敏感算子优先用平台标准库。
3. **性能折损是常态**：兼容路线折损通常 10%-40%，性能不可接受时需换库、优化或重写。
4. **库依赖是隐藏工作量**：cuBLAS、cuDNN、NCCL 等均需找到替代品，评估阶段就要列全。
5. **构建系统迁移容易被低估**：CMake、算子注册、JIT 编译等需作为独立任务排期。
6. **多卡与分布式是另一个战场**：通信库迁移独立于单算子迁移，建议单卡验证通过后再启动。
7. **版本兼容性要锁死**：SDK、驱动、框架插件需使用官方推荐组合，并在 CI 中锁定。
8. **不要一次性全量迁移**：先迁移 1-2 个代表性算子跑通全流程，验证可行性后再批量推进。
9. **文档和社区是重要资源**：优先查官方迁移指南和示例，建立内部迁移知识库。
10. **保持可回退能力**：用抽象层隔离硬件相关代码，保留原始 CUDA 路径，通过开关切换。

**先评估、再选路、小步验证、精度兜底、性能兜底、保持可回退。** 迁移不是一次性的代码转换，而是一个需要持续验证和优化的工程过程。

## 算子不支持时，如何判断是否能用已有算子组合替代？
答：**判断能否组合替代，核心看四点：数学可分解、精度可接受、性能可接受、逻辑可维护。** 四者缺一，就应考虑重写自定义算子，而非强行拼凑。
### 判断维度
**1. 数学可分解性**
算子的数学定义能否用已有算子等价表达。逐元素复合（如 Swish = x * sigmoid(x)）、归约类（如 Softmax）、矩阵运算（如 Linear = matmul + add）、归一化类（如 LayerNorm）通常可分解；依赖硬件特定指令、精细内存布局或复杂控制流的算子则难以分解。
**2. 精度可接受性**
分解后运算步骤增加，可能引入误差累积。需关注是否引入额外浮点运算、中间结果精度是否足够、是否有数值不稳定风险，并与原始 GPU 结果逐元素比对验证。
**3. 性能可接受性**
数学等价不等于性能等价。关注算子数量增加倍数、中间张量显存占用、额外 kernel launch 与同步开销。经验法则：算子数量增加不超过 3-5 倍通常可接受，超过 10 倍需谨慎。
**4. 实现复杂度与可维护性**
组合逻辑是否易于表达、是否需要大量手工形状操作、换输入形状是否需重新调整。经验法则：组合节点超过 20-30 个或需大量手工形状操作时，直接重写更划算。

### 二、实操判断流程

算子不支持 → ①数学能否分解？→ ②原子算子是否齐全？→ ③精度是否可接受？→ ④性能是否可接受？→ ⑤逻辑是否可维护？→ 全部通过则采用组合替代，任一环节不通过则考虑重写自定义算子。

### 三、常见可组合替代示例

| 原算子 | 组合替代 | 注意事项 |
| --- | --- | --- |
| Swish / SiLU | x * sigmoid(x) | 精度几乎无损 |
| GELU | 0.5 * x * (1 + erf(x/√2)) | erf 实现差异影响精度 |
| Softmax | exp(x-max) / sum(exp(x-max)) | 减 max 保证数值稳定 |
| LayerNorm | (x-mean) / sqrt(var+eps) * γ + β | 需 reduce 与 rsqrt |
| Linear | matmul(x, W^T) + b | 标准分解 |
| Conv2D（小核） | im2col + matmul | 显存开销大 |
| Attention | softmax(QK^T/√d) V | 性能远不如 FlashAttention |
| BatchNorm（推理） | 折叠为缩放平移 | 推理时可简化 |
| Dropout（推理） | 恒等映射 | 直接省略 |
| L2 Normalize | x / sqrt(sum(x²)+eps) | 注意 eps 与广播 |

### 四、关键注意事项

1. 数学等价 ≠ 数值等价，浮点运算顺序不同会带来微小差异，必须验证。
2. 明确组合替代是临时过渡还是长期方案。
3. 善用目标平台图优化，图编译器可能自动融合组合算子。
4. 形状操作（transpose、reshape、concat）可能触发隐式拷贝，成为性能瓶颈。
5. 将验证过的组合方案沉淀为内部模板库，便于复用。
6. 精度敏感场景务必用原始 GPU 结果逐元素比对。
7. 性能不达标时优先尝试算子融合，其次重写热点算子。

## 如果结果正确但性能只有 NVIDIA 平台的很小一部分，如何定位问题？
答：
结果正确但性能远低于 NVIDIA，说明算法逻辑没错，问题出在**代码中残留的 CUDA 硬件假设**与目标平台不匹配。定位思路：**先判断瓶颈类型，再排查 CUDA 惯性假设。**

**Roofline 判断瓶颈类型 → Profiling 定位具体耗时算子 → 检查该算子的 tile/同步/精度实现是否带有 CUDA 惯性假设 → 用 AOE 或手动重写关键路径。**

### 一、先判断瓶颈类型

用目标平台的 Profiling 工具（昇腾 msProf / 海光 rocprof）采集数据，看 Roofline 图：

- **访存受限**：大部分时间在等内存，需优化数据搬运通路和重复搬移。
- **计算受限**：计算单元接近饱和，需换计算单元、降精度或减少计算量。
- **流水利用率低**：未达硬件上限，问题在流水编排和同步策略。

### 二、排查四类 CUDA 惯性假设

**1. 共享内存 Tile 尺寸假设**
CUDA 常动态配置 shared memory tile，但部分国产芯片的共享缓冲区是固定大小（如昇腾 L0B 固定 32KB）。硬编码 CUDA 风格 tile 会导致数据溢出到更慢的层级。

**2. 同步与流水编排假设**
CUDA 的 `__syncthreads()`、异步拷贝语义在国产芯片上可能不同。算子融合时，本可并行的算子可能因保序约束被强制串行化，导致性能骤降。

**3. 编译期决策已固化**
部分平台（如昇腾 ATC）在编译阶段就固化了 tiling 策略和实现选择，运行时无法更改。若编译期选错实现，只能重新编译或用 AOE 调优。

**4. 线程/并行粒度不匹配**
CUDA 是 32 线程 Warp，部分国产芯片是 64 线程 Wavefront。依赖 `warpSize=32` 的逻辑会重复计算或空转，结果正确但性能折半。

### 三、用 Profiling 数据定位

重点看：MTE/Vector/Cube cycle 占比（判断瓶颈单元）、UB/L1 实测带宽（是否远低于理论值）、bank 冲突率、L2 命中率。昇腾 MindStudio Insight 的 Top Warp Stall Reason 可直接看流水线停顿主因。
