## 1. 岗位背景理解

### 1.1 公司为什么做 LLM 软件栈？

**问题：为什么存储芯片公司开始进入大模型领域？**

回答：

大模型的发展正在改变计算系统瓶颈。

传统 AI 主要关注计算能力，例如 FLOPS，但是 LLM 推理阶段，尤其 Decode 阶段，性能越来越受到 Memory Wall 限制。

大模型推理链路：

```text
模型权重
    |
Memory
    |
计算单元
    |
输出Token
```

随着模型规模增加：

* 参数规模增长
* 上下文长度增加
* KV Cache 增长

导致数据搬运成为主要成本。

LLM 推理需要关注：

* Memory Bandwidth
* Cache效率
* 数据调度
* 存储层级

存储芯片公司的优势不是和 GPU 竞争算力，而是在：

> 计算 + 存储 + 数据移动优化方向形成软硬件协同。

## 2. 为什么 LLM 推理存在 Memory Bound？

### 2.1 Prefill 和 Decode 区别

**问题：为什么说 Decode 阶段是 Memory Bound？**

回答：

LLM 推理分为两个阶段：

### Prefill

输入完整 Prompt。

特点：

* 一次处理大量 Token
* GEMM计算量大
* 数据复用率高

主要瓶颈：

Compute Bound。

### Decode

逐 Token 生成。

每生成一个 Token，需要访问：

* 当前 Query
* 历史 Key
* 历史 Value

即：

```text
Q_new

+
K_1...K_n

+
V_1...V_n
```

随着上下文增长：

$$
KVCache \propto SequenceLength
$$

访问数据越来越多。

判断瓶颈：

$$
AI=\frac{FLOPs}{MemoryBytes}
$$

当 Arithmetic Intensity 较低时：

性能主要受 Memory Bandwidth 限制。

## 3. 如果设计面向 LLM 的芯片，需要关注什么？

### 3.1 芯片架构方向

**问题：如果让你设计一颗面向 LLM 推理的芯片，你认为重点在哪里？**

回答：

重点不是单纯增加 TOPS，而是优化数据流。

主要方向：

### 1. Memory Hierarchy

典型层级：

```text
Register

↓

SRAM

↓

HBM

↓

DDR

↓

SSD
```

不同数据应该放在不同层级。

例如：

| 数据         | 位置       |
| ---------- | -------- |
| 正在计算的数据    | SRAM/HBM |
| 近期KV Cache | HBM/DDR  |
| 长期历史数据     | SSD      |

---

### 2. KV Cache 管理

KV Cache 是长上下文场景的主要内存压力。

优化：

* KV Cache Quantization
* Paged KV Cache
* Offloading
* Compression

---

### 3. 数据移动优化

性能瓶颈越来越来自：

```text
Data Movement
```

而不是：

```text
Compute
```

因此需要：

* 高带宽互联
* 数据预取
* Cache优化

## 7. Attention 和 FlashAttention

### 7.1 为什么FlashAttention快？

回答：

普通Attention：

需要保存：

$$
QK^T
$$

空间复杂度：

$$
O(N^2)
$$

FlashAttention：

采用：

* Tiling
* Online Softmax
* SRAM复用

核心：

减少：

HBM访问次数。

不是减少计算量，而是减少数据移动。

---

## 8. KV Cache优化

### 8.1 KV Cache为什么占显存？

回答：

每层保存：

* Key
* Value

大小：

$$
Memory=
2 \times Layers \times SeqLen \times Heads \times HeadDim \times Bytes
$$

影响因素：

* 模型层数
* 上下文长度
* Batch大小

---

### 8.2 如何优化KV Cache？

#### 方法1：量化

FP16：

2 Bytes

INT8：

1 Byte

减少约50%存储。

---

#### 方法2：PagedAttention

传统：

```text
连续Memory

Request1

Request2
```

问题：

碎片。

Paged：

```text
Page1

Page2

Page3
```

类似虚拟内存管理。

优势：

* 动态分配
* 降低碎片

---

#### 方法3：KV Cache Offload

分层：

```text
HBM

↓

DDR

↓

SSD
```

热数据：

高速Memory。

冷数据：

低速Memory。

关键：

通过：

* Prefetch
* Async IO
* Compression

隐藏延迟。

### 14.3 入职90天计划？

回答：

#### 整体三段对照

| 阶段 | 定位 | 关键动作 | 检验标准 |
|---|---|---|---|
| 0–10 天 | 了解 | 读代码、跑通、对齐基线、确认验收标准、摸清团队短期目标 | 能说清我负责什么、什么算合格、上下游是谁 |
| 10–30 天 | 掌握 | 独立完成一个小需求、量化前后、理清上下游协作 | 拿出一个可复现的小增量，知道影响谁、被谁影响 |
| 30–90 天 | 负责 | 做深、做稳、做可交接、延伸半步 | 换人能跑、能验证、知道边界和下一步 |

#### 第一阶段（0–10 天）：了解负责内容、环境、上下游、验收标准、团队短期目标

**目标**：从“不知道自己要干什么”变成“能说清楚我负责什么、什么算合格、我的输入输出是谁”。

**1. 负责内容**
- 读完你负责模块的代码/文档/配置，画出模块图：输入是什么、输出给谁、依赖谁、被谁依赖。
- 跑通经过你模块的主路径，哪怕只是最简场景。
- 记录你还没看懂的点，形成一份“不懂清单”。

**2. 开发测试环境**
- 搭好本地/远程开发环境，确认能编译、能跑、能调试。
- 找到团队现有的测试入口和 benchmark 口径，搞清楚什么指标对应你负责的模块。
- 确认代码提交、review、CI 的流程和规范。

**3. 上下游情况**
- 找直属 leader 对齐一次，确认三件事：
  - 我这块当前最被诟病的是什么？
  - 什么指标达标了算我合格？
  - 有没有已知但没空修的坑，是我这块的？
- 找上下游各聊一次，搞清楚你的输入从哪来、输出给谁用。

**4. 验收标准**
- 把 leader 说的“合格”翻译成具体指标：延迟、显存、吞吐、命中率，取决于你负责什么。
- 确认当前基线大概是多少，以及有没有现成的性能报告可参考。

**5. 团队短期目标**
- 搞清楚团队未来 1–3 个月的重点是什么，你的模块在其中处于什么位置。
- 判断你负责的这块，短期最可能被要求解决什么问题。

**产出**：一份个人笔记——模块图 + 当前基线 + 验收指标 + 已知坑 + 不懂清单 + 团队短期重点。

**检验**：10 天时你能说清楚——我负责什么、现在什么水平、什么算合格、我的上下游是谁、团队短期要什么。

#### 第二阶段（10–30 天）：掌握负责内容，独立完成一个小需求，清晰认识上下游

**目标**：从“知道”变成“能独立交付一个小需求”，并且对上下游从“认识”变成“知道怎么协作”。

**1. 掌握负责内容**
- 不再只是读代码，而是能独立修改你负责的模块，并能解释每一处改动的理由。
- 把第一阶段的不懂清单逐条消掉，剩下的写成“已知边界”。
- 注意：不是“完全掌握”，而是“掌握到能独立完成一个小需求，并知道自己的边界在哪”。

**2. 独立完成一个小需求**
- 从第一阶段记下的“已知坑”或 leader 给的任务里，挑一个范围最小、可独立闭环、不跨模块的需求。
- 先量化再动手：改之前记录基线，改完给出前后对比。
- 只动你负责的模块，不越界。需要别人配合的，记下来，这个阶段不碰。
- 输出一条结论：“我改了 X，指标 Y 从 A 到 B，复现方式是 Z”。

**3. 清晰认识上下游**
- 不只是知道上下游是谁，而是知道：你的输出被谁用、他们关心什么指标、你的改动会影响谁。
- 至少完成一次跨模块沟通：确认你的改动对上下游的影响，以及他们对你的输入要求。
- 把上下游的接口、约定、边界写成自己的笔记，避免后面踩坑。

**产出**：
- 一个已完成的小需求，带前后数据
- 一份上下游接口/边界笔记
- 更新后的“已知边界”清单

**检验**：30 天时你能拿出一个可复现的小增量，并能说清楚你的改动影响了谁、被谁影响。

#### 第三阶段（30–90 天）：独立负责一块，并让结果可量化、可交接

**目标**：从“完成一个小需求”变成“我负责的这块，我能说清楚它现在什么水平、我改了什么、边界在哪、下一步该动哪”。

**1. 做深**
- 不换方向，把第二阶段的小需求扩展到 2–3 个典型场景，量化收益边界，明确哪些场景不适用。
- 在你负责的模块内，固定一套可复现的测试口径（模型规模、上下文长度、并发，或你模块对应的指标），记录当前基线。

**2. 做稳**
- 补回归测试，让你改过的东西别人也能验证。
- 写清楚适用场景和边界，避免别人误用。
- 如果你负责的模块有对外接口或配置，把默认值和边界写清楚，给最小使用说明。

**3. 做可交接**
- 输出属于你负责模块的“使用/验证说明 + 基线数据 + 已知边界”。
- 整理一份未解决问题清单，明确哪些是你没解决的、哪些是需要别人配合的。

**4. 延伸半步（可选，看你想要多大话语权）**
- 基于你掌握的基线，主动向 leader 提一个“我这块下一步该动哪”的建议，并给出理由和数据支撑。
- 如果你的优化依赖别的模块，主动找对方对齐一次，提出你的需求和边界，但不替他们做决定。

**产出**：
- 模块级“使用/验证说明 + 基线数据”
- 一条明确结论：“我负责的 X，当前基线是 A，我优化到 B，适用场景是 C，不适用 D”
- 未解决问题清单
- （可选）一个你主动提出的下一步优化建议

**检验**：90 天时，换一个人能照着你的说明跑起来、验证，并知道当前基线和你没解决的问题。

## 15. 面试定位总结

对于存储芯片公司的LLM工程师岗位，核心能力不是：

“会写CUDA Kernel”。

而是：

> 理解LLM推理的数据流特点，并能够连接模型、Runtime、算子和存储硬件，实现软硬件协同优化。

个人定位：

```text
LLM推理系统工程师

+

CUDA Kernel优化能力

+

C++ Runtime开发能力

+

Memory优化意识
```

这是与Intel、Micron、西部数据背景技术团队更匹配的方向。
