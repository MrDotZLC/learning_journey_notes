## 推理框架：vLLM、SGLang 与 RadixAttention
### RadixAttention 的核心思想是什么？
答：SGLang 将 KV Cache 复用与 Radix Tree 结合，根据 Token Prefix 查找已有的缓存节点。如果新请求与历史请求共享前缀，就可以复用对应前缀的 KV Cache，只对尚未计算的后缀执行 Prefill。系统还需要处理节点分裂、引用关系、缓存淘汰和显存回收等问题。它的收益取决于请求之间的前缀重合程度、缓存命中率以及缓存管理开销。

### RadixAttention 与 PagedAttention 有什么区别？
|比较维度|PagedAttention|RadixAttention|
|---|---|---|
|主要目标|减少 KV Cache 内存分配与碎片问题|提高重复前缀的缓存复用率|
|数据组织|逻辑块与物理块映射|Token Prefix 的树形索引与缓存节点|
|关键操作|Block 分配、映射、读写与回收|Prefix 匹配、缓存共享、节点分裂与淘汰|
|典型收益|显存利用率、并发请求承载能力|减少重复 Prefill 计算、降低 TTFT|
|主要挑战|Block Table、内存管理和访问效率|引用计数、缓存一致性、淘汰与并发安全|

### Radix Cache 命中后为什么不能直接跳过所有 Prefill？
答：
只有命中的 Token Prefix 对应的 KV Cache 可以复用，未命中的后缀仍需计算；此外，模型版本、Adapter、位置编码、Attention Mask、KV 数据格式等条件必须兼容，才能安全复用缓存。

### 如何将 SGLang 适配到自研 AI 芯片？
答：
1. 设备层： 接入设备发现、Context、Stream、Event、内存分配和 Kernel Launch。
2. 算子层： 实现或移植 GEMM、RMSNorm、RoPE、Attention、Sampling 等关键算子。
3. KV Cache 层： 支持目标芯片上的缓存分配、Block Table、内存回收、数据类型和布局。
4. 执行层： 适配 Model Runner、Scheduler、Batching、图执行及同步机制。
5. 框架层： 验证模型加载、算子注册、异常处理、取消请求与动态形状。
6. 性能层： 对比 TTFT、TPOT、吞吐、缓存命中率、显存峰值和多请求稳定性。
关键在于区分可复用的上层调度逻辑与依赖特定设备的底层实现。如果芯片没有兼容 CUDA 的 Runtime，就不能简单替换设备名称，而必须提供可用的后端执行路径。

### 如何实现 KV Cache 的引用计数与并发回收？
答：
> 避免共享 Prefix 误释放，本质是保证**引用计数归零才回收**，并且这个判断和回收必须是原子的。

**三个关键机制：**

**1. 共享必 incr，释放必 decr**
任何请求命中已缓存前缀、或 fork 出子序列时，都对共享块 `incr`；释放时严格 `decr`。`incr` 必须发生在使用之前，`decr` 发生在停用之后。

**2. 只有 ref_count == 0 才可回收或驱逐**
只要还有活跃请求引用（`ref_count > 0`），块就不能被物理回收，也不能被前缀缓存的 LRU 驱逐。驱逐前必须二次校验计数。

**3. 检查归零与回收必须原子**
并发下最危险的是"读到 0 → 准备释放 → 期间被别人 incr"的窗口。必须用锁或 CAS 把"判断归零 + 移出空闲队列"做成一个原子操作。

**补充一句加分项：**
> 配合写时复制（CoW），`ref_count > 1` 时写入先复制再改，避免共享内容被污染。

### 如何处理请求取消、超时和异常退出？
答：
> 取消、超时、异常退出的处理，核心是**在资源持有者可能已经消失的情况下，仍然能正确判断何时可以安全回收 KV Cache**。难点在于：你无法依赖请求方主动通知，必须设计一套“最坏情况下的兜底回收机制”。

#### 场景一：请求取消（用户主动 abort）
**特征**：客户端明确调用 abort 接口，请求方还在，能正常通信。
**处理方式**：正常维护引用计数，标记块资源可以回收，真正的块资源回收要等到本轮调度完成。

#### 场景二：超时（请求方失联但资源未释放）
**特征**：客户端崩溃、网络断开、或长时间无响应，但预填充实例还持有 KV 块等待传输。
**处理方式（以 PD 分离场景为例）**：只要还有该请求的decode任务在运行，就一直等待，没有活跃的decode任务后，调度器等待一段时间（30s）后，清理KV 块。期间重连上，则继续调度运行。

#### 场景三：异常退出（客户端断开、进程被杀）
**特征**：最恶劣的情况——请求方直接消失，没有任何 clean shutdown 信号。
**处理方式**：除了按顺序释放资源，考虑路径中同时释放的可能，保证每个释放步骤是幂等的。
- **客户端断开检测**：在流式生成中，`asyncio.CancelledError` 可以被捕获，触发 `engine.abort()`，释放 KV 和调度槽位。但要注意，**非流式路径**也要覆盖，不能只处理流式场景。
- **跨传输的“未完成义务”追踪**：如果请求涉及多个异步传输（比如同时有 recv 和 send 在飞），不能“第一个完成信号到了就释放”。必须等**所有未完成传输都结束**，才允许释放块。否则会出现：send 先完成 → 块被释放 → 另一个请求复用 → recv 还在 DMA 写入 → 数据污染。
- **幂等释放**：abort 可能在多个路径上被触发（调度器 finish、传输完成回调等），释放操作必须幂等，重复结束不会再次释放。
- **残留信号防御**：传输完成信号到达时，请求可能已经被 abort 并释放。此时**不能硬断言** `req_id in self.requests`，否则一个断开的客户端会触发 EngineCore 崩溃，导致该副本上所有租户的请求全部 500。

### 如何设计支持不同 Batch Size、Sequence Length 和 Head Dimension 的 Attention Kernel？
答：整体采用FLashAttention。
1. 对不同 Batch Size，调整 Grid 和并行任务粒度；
2. 对不同 Sequence Length，选择合适的 Query Tile 和 Key Tile，长序列采用分块流水，短序列减少分块和调度开销；
3. 对不同 Head Dimension，则根据维度选择 Warp 数、向量化宽度和寄存器布局，并针对常见维度如 64、128 做专门优化。

工程上，我会提供多个经过调优的 Kernel Variant，通过输入形状、数据类型、是否 Causal、硬件能力等元数据进行 Dispatch。最后使用数值正确性测试和 Benchmark，结合 Nsight 分析寄存器压力、Occupancy、访存带宽和 Kernel Launch 开销，确保不同形状下都具有稳定性能。

### 如何区分 TTFT、TPOT、端到端延迟与吞吐量之间的权衡？
答：
根据业务目标决定优化方向。如果是交互式对话，优先关注 TTFT 和 TPOT；如果是离线批量生成，通常更关注吞吐量和单位 Token 成本。
增大 Batch Size 往往可以提高 GPU 利用率和吞吐量，但可能增加排队时间、TTFT 和单请求 TPOT。
因此需要联合观察 P50/P95/P99 延迟、输出长度和吞吐量，通过 Continuous Batching、KV Cache 管理和 Prefill/Decode 调度寻找合适的平衡点，而不是单纯追求最高吞吐量。

### 如何用 C++ 实现 KV Cache Manager？Prefix Cache 在其中怎么实现的？
答：
数据结构：一整块设备缓冲按层切片，块大小固定，vector 管理已使用的块，list 管理未使用的块。
分配策略： 采用固定大小 Block，支持批量申请、释放、复用和显存容量检查；避免每个 Token 单独申请显存导致的频繁分配。
并发控制： 使用 Mutex 或细粒度锁保护空闲队列和引用计数，明确请求取消、异常退出及缓存淘汰时的所有权规则。

### 新平台 GPU 适配需要考虑哪些维度？
答：

|适配维度|需要检查的内容|常见风险|
|---|---|---|
|编译与运行时|编译器、运行时 API、设备查询、Stream 与 Event|CUDA API 不能直接假设可用|
|线程执行模型|Thread、Warp/Wavefront、Block、同步原语|线程布局或同步语义不同|
|片上存储|Shared Memory 对应机制、容量、Bank 组织|原有 Tile 超出资源限制或访存冲突|
|矩阵计算|矩阵指令、支持的数据类型、Tile 约束|Tensor Core/MMA 实现不能直接复用|
|数学库|GEMM、Softmax、归约等算子库支持|缺少对应实现或调用路径不兼容|
|编译器优化|寄存器分配、指令生成、向量化与流水线|同一源码在不同平台生成不同质量的代码|
|Profiling|时间线、硬件计数器、内存和执行效率指标|无法使用 NVIDIA 专属工具获得相同指标|

### 新平台怎么进行算子迁移与优化？
答：
我会分五个阶段进行算子迁移与优化。
1. 算子盘点与正确性验证： 梳理原平台的算子类型、数据类型、Tensor Layout、Shape、精度要求及上下游依赖，建立覆盖典型 Shape 和边界条件的测试集，确保新平台计算结果与原平台一致。
2. 算子适配： 优先复用新平台已有的高性能算子库；如果接口或数据布局不兼容，就通过适配层转换参数、Layout 和数据类型；对于缺失或性能较差的算子，再使用新平台的编程模型重新实现。
3. 性能分析： 建立单算子 Benchmark，测量延迟、吞吐量、显存带宽和计算单元利用率，判断算子属于 Compute-bound 还是 Memory-bound，避免盲目优化。
4. 针对性优化： 对访存瓶颈优化数据合并访问、数据复用和 Tile 划分；对计算瓶颈优化线程映射、向量化、指令选择和 Tensor Core 等矩阵计算单元的利用；同时考虑 Kernel Fusion、减少 Launch 开销及临时 Tensor 的分配。
5. 端到端验证： 不仅比较单算子性能，还要在完整模型上验证数值精度、端到端延迟、吞吐量和显存占用，排查数据布局转换、跨算子同步等额外开销，并将优化结果纳入自动化回归测试。

迁移过程中，我会优先保证正确性，再根据 Profiling 数据决定优化方向，最后通过真实模型负载验证收益，避免单算子加速但整体性能反而下降。

| 追问                     | 回答要点                                                         |
| ---------------------- | ------------------------------------------------------------ |

最后记住一个原则： 算子迁移解决的是“能不能正确运行”，算子优化解决的是“能否充分利用新硬件”。两者必须分阶段验证，不能把代码转换成功等同于性能优化完成。

### 如果要求将 FlashAttention 移植到沐曦 GPU，如何回答？
答：
我会把适配过程分为四个阶段。

第一阶段是功能与环境确认，明确目标 GPU 型号、MACA 工具链版本、支持的数据类型、矩阵计算能力、Shared Memory 和寄存器限制，并确认现有 Attention 算子库是否已有可复用实现。

第二阶段是建立正确性基线，先实现或运行一个简单的 Attention 参考版本，对比 FP32 参考结果与目标平台结果，覆盖不同序列长度、Head Dimension、Causal Mask 和边界条件。

第三阶段是性能迁移。我会优先保留 FlashAttention 的 IO-aware Tiling 和 Online Softmax 算法，再根据目标硬件重新调整 Tile 大小、线程布局、数据类型、矩阵计算指令和流水线。对于不能直接迁移的 NVIDIA 专用指令，需要使用 MACA 对应能力或设计替代实现。

第四阶段是性能验证与回归。统一 Benchmark 条件，对比延迟、吞吐量、显存占用、精度误差和不同输入形状下的表现，并通过目标平台的 Profiling 工具定位瓶颈，逐步优化，而不是一次性重写整个 Kernel。

### 如果 NVIDIA 上更快的 FlashAttention 实现在沐曦上变慢了，怎么办？
答：
结果正确但性能远低于 NVIDIA，说明算法逻辑没错，问题出在**代码中残留的 CUDA 硬件假设**与目标平台不匹配。定位思路：**先判断瓶颈类型，再排查 CUDA 惯性假设。**

**Roofline 判断瓶颈类型 → Profiling 定位具体耗时算子 → 检查该算子的 tile/同步/精度实现是否带有 CUDA 惯性假设 → 用 AOE 或手动重写关键路径。**

#### 一、先判断瓶颈类型

用目标平台的 Profiling 工具（昇腾 msProf / 海光 rocprof）采集数据，看 Roofline 图：

- **访存受限**：大部分时间在等内存，需优化数据搬运通路和重复搬移。
- **计算受限**：计算单元接近饱和，需换计算单元、降精度或减少计算量。
- **流水利用率低**：未达硬件上限，问题在流水编排和同步策略。

#### 二、排查四类 CUDA 惯性假设

**1. 共享内存 Tile 尺寸假设**
CUDA 常动态配置 shared memory tile，但部分国产芯片的共享缓冲区是固定大小（如昇腾 L0B 固定 32KB）。硬编码 CUDA 风格 tile 会导致数据溢出到更慢的层级。

**2. 同步与流水编排假设**
CUDA 的 `__syncthreads()`、异步拷贝语义在国产芯片上可能不同。算子融合时，本可并行的算子可能因保序约束被强制串行化，导致性能骤降。

**3. 编译期决策已固化**
部分平台（如昇腾 ATC）在编译阶段就固化了 tiling 策略和实现选择，运行时无法更改。若编译期选错实现，只能重新编译或用 AOE 调优。

**4. 线程/并行粒度不匹配**
CUDA 是 32 线程 Warp，部分国产芯片是 64 线程 Wavefront。依赖 `warpSize=32` 的逻辑会重复计算或空转，结果正确但性能折半。

#### 三、用 Profiling 数据定位

重点看：MTE/Vector/Cube cycle 占比（判断瓶颈单元）、UB/L1 实测带宽（是否远低于理论值）、bank 冲突率、L2 命中率。昇腾 MindStudio Insight 的 Top Warp Stall Reason 可直接看流水线停顿主因。

### 如果目标平台没有完全对应的 Tensor Core 指令怎么办？
答：
如果目标平台没有完全对应的 Tensor Core 指令，我会从计算语义、硬件能力和性能收益三个方面评估，不会直接照搬原平台的指令实现。

第一，寻找等价计算路径。如果目标平台有类似矩阵计算单元，就使用其对应的矩阵乘法指令或高性能算子库，重新适配 Tile 大小、数据类型、线程布局和数据搬运方式。

第二，调整算法和数据精度。如果矩阵指令支持的精度或计算形状不同，可以考虑 FP16、BF16、INT8 等目标平台支持的数据类型，并验证精度误差；如果没有合适的矩阵计算单元，就使用 SIMD/SIMT、向量化指令或普通计算单元实现矩阵乘法。

第三，重新进行性能调优。根据目标平台的计算吞吐量、访存带宽、寄存器和 Shared Memory 容量，调整分块策略、数据复用和并行粒度，并通过 Benchmark 和 Profiling 确定最优实现。

最后，我会验证数值精度、边界条件和端到端性能，确保替代实现不仅能够正确运行，而且在目标平台上具有实际收益。

面试总结： Tensor Core 是一种硬件实现方式，而不是算法本身。迁移时应保留计算语义，根据目标平台的硬件能力重新选择指令、数据精度和并行策略；如果缺少等价硬件，就采用通用计算路径，并通过实测权衡性能与精度。

### 如何确保跨平台精度一致？
答：我会从统一计算语义、控制数值误差、分层验证和端到端回归四个方面确保跨平台精度一致。

第一，统一计算语义，包括输入输出的数据类型、累加精度、量化参数、舍入模式、溢出处理以及算子实现中的边界条件，避免不同平台因计算规则不同产生误差。

第二，控制数值误差。对于 FP32、FP16、BF16、INT8 等不同精度路径，明确允许的误差范围；如果目标平台使用不同的矩阵计算指令或累加精度，需要评估误差是否会逐层累积，必要时采用更高精度累加或对敏感算子使用混合精度。

第三，建立分层验证机制。先验证单算子的输出误差，再验证模型中间层输出，最后比较端到端结果。常用指标包括最大绝对误差、最大相对误差、RMSE，以及任务相关指标，例如分类准确率或检测 mAP。对于接近零的数值，相对误差可能失去参考价值，因此需要结合绝对误差判断。

第四，进行自动化回归测试。覆盖不同 Tensor Shape、边界条件、随机输入和极端输入，并在固定测试集上比较各平台结果。对于量化模型，还要验证校准参数、量化与反量化过程及最终任务精度。

面试总结： 跨平台精度一致不一定意味着每个浮点数逐位相同，而是要保证计算语义一致、数值误差在约定阈值内、端到端任务指标满足要求。如果业务要求确定性或逐位一致，则还需要进一步统一运算顺序、舍入规则和确定性算法。浮点加法具有非结合性，不同硬件的指令调度和累加顺序都可能造成细微差异。

### 如何设计 内存池
答：我会先明确内存池的使用场景，包括分配大小分布、并发线程数、分配释放频率以及是否涉及异步 GPU 操作。
对于高频的小块分配，可以采用预分配与分级 Block 管理，减少系统分配器或 GPU Runtime 的调用开销；对于多线程访问，可以通过 Thread-local Cache 或分片管理减少全局锁竞争。
对于 GPU 内存，还必须考虑异步 Kernel 的执行生命周期，不能仅根据 CPU 侧函数返回就释放仍被 GPU 使用的资源。最后通过分配延迟、吞吐量、碎片率和并发压力测试评估实际收益。
