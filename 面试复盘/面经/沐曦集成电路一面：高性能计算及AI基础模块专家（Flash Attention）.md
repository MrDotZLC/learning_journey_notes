## 面经


## FLashAttention

### 概述 FLashAttention
答：
FlashAttention 是一种面向 GPU 的高性能 Attention 算法，核心思想是通过 分块计算（Tiling）、在线 Softmax（Online Softmax）和算子融合（Kernel Fusion），减少 GPU Global Memory 的读写次数，从而提升 Attention 的计算效率。

传统 Attention 的计算公式为：

$$ \operatorname{Attention}(Q,K,V)=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

其中，\(Q\)、\(K\)、\(V\) 分别是 Query、Key、Value 矩阵，\(d\) 是每个 Attention Head 的维度。传统实现会显式计算并存储 \(N\times N\) 的 Attention Score 矩阵，其中 \(N\) 是序列长度，导致显存占用和访存开销随序列长度平方增长。

FlashAttention 将 \(Q\)、\(K\)、\(V\) 切分成多个 Tile，利用 GPU 的 Shared Memory 和寄存器分块计算，每次只处理部分 Attention Score，通过 Online Softmax 逐块更新归一化结果，避免将完整的 \(N\times N\) 矩阵写入 Global Memory。同时，将矩阵乘法、Softmax 和与 \(V\) 的矩阵乘法尽可能融合到同一个 CUDA Kernel 中，减少中间结果的显存读写和 Kernel Launch 开销。

需要注意，FlashAttention 并没有消除 Attention 的 \(O(N^2d)\) 计算复杂度，而是优化了 IO 复杂度和显存占用；它属于精确 Attention 算法，不是通过稀疏化或近似计算来减少注意力计算量。

性能收益主要来自减少 HBM 访问、避免物化完整的 Attention 矩阵，以及降低中间 Tensor 的存储开销；实际加速比取决于 GPU 架构、序列长度、Head Dimension 和 Tile 配置。

面试中可以进一步补充：FlashAttention-2 进一步优化了线程块划分、Warp 间工作分配和并行效率；FlashAttention-3 则针对 NVIDIA Hopper 等架构利用异步执行和 Tensor Core 能力提升性能。

一句话总结：FlashAttention 的本质是以 IO-aware 的分块计算和在线归一化，避免大规模中间结果落入显存，在保持精确 Attention 结果的同时提升 GPU 执行效率。

### Softmax Online 原理
答：softmax算法是通过遍历3次数据，获得全局最大值、全局归一化因子，完成计算。

假设将 \(K,V\) 按序列维度分成多个 Block。处理当前 Block 前，维护三个状态：当前最大 Logit \(m\)、归一化指数和 \(l\)、输出分子向量 \(u\)。

| 为什么理论带宽很高，实测却不快？                         | 可能受 Occupancy、指令依赖、同步、非合并访存、启动开销或实际有效带宽限制                                   |

## 沐曦 GPU 适配

### 新平台 GPU 适配需要考虑哪些维度？
答：

|适配维度|需要检查的内容|常见风险|
|---|---|---|
|编译与运行时|编译器、运行时 API、设备查询、Stream 与 Event|CUDA API 不能直接假设可用|

### 新平台怎么进行算子迁移与优化？
答：
我会分五个阶段进行算子迁移与优化。
1. 算子盘点与正确性验证： 梳理原平台的算子类型、数据类型、Tensor Layout、Shape、精度要求及上下游依赖，建立覆盖典型 Shape 和边界条件的测试集，确保新平台计算结果与原平台一致。
2. 算子适配： 优先复用新平台已有的高性能算子库；如果接口或数据布局不兼容，就通过适配层转换参数、Layout 和数据类型；对于缺失或性能较差的算子，再使用新平台的编程模型重新实现。
3. 性能分析： 建立单算子 Benchmark，测量延迟、吞吐量、显存带宽和计算单元利用率，判断算子属于 Compute-bound 还是 Memory-bound，避免盲目优化。
4. 针对性优化： 对访存瓶颈优化数据合并访问、数据复用和 Tile 划分；对计算瓶颈优化线程映射、向量化、指令选择和 Tensor Core 等矩阵计算单元的利用；同时考虑 Kernel Fusion、减少 Launch 开销及临时 Tensor 的分配。
5. 端到端验证： 不仅比较单算子性能，还要在完整模型上验证数值精度、端到端延迟、吞吐量和显存占用，排查数据布局转换、跨算子同步等额外开销，并将优化结果纳入自动化回归测试。

迁移过程中，我会优先保证正确性，再根据 Profiling 数据决定优化方向，最后通过真实模型负载验证收益，避免单算子加速但整体性能反而下降。

### 如果要求将 FlashAttention 移植到沐曦 GPU，如何回答？
答：
我会把适配过程分为四个阶段。

第一阶段是功能与环境确认，明确目标 GPU 型号、MACA 工具链版本、支持的数据类型、矩阵计算能力、Shared Memory 和寄存器限制，并确认现有 Attention 算子库是否已有可复用实现。

第二阶段是建立正确性基线，先实现或运行一个简单的 Attention 参考版本，对比 FP32 参考结果与目标平台结果，覆盖不同序列长度、Head Dimension、Causal Mask 和边界条件。

第三阶段是性能迁移。我会优先保留 FlashAttention 的 IO-aware Tiling 和 Online Softmax 算法，再根据目标硬件重新调整 Tile 大小、线程布局、数据类型、矩阵计算指令和流水线。对于不能直接迁移的 NVIDIA 专用指令，需要使用 MACA 对应能力或设计替代实现。

第四阶段是性能验证与回归。统一 Benchmark 条件，对比延迟、吞吐量、显存占用、精度误差和不同输入形状下的表现，并通过目标平台的 Profiling 工具定位瓶颈，逐步优化，而不是一次性重写整个 Kernel。

### 如果 NVIDIA 上更快的 FlashAttention 实现在沐曦上变慢了，怎么办？
答：
结果正确但性能远低于 NVIDIA，说明算法逻辑没错，问题出在**代码中残留的 CUDA 硬件假设**与目标平台不匹配。定位思路：**先判断瓶颈类型，再排查 CUDA 惯性假设。**

**Roofline 判断瓶颈类型 → Profiling 定位具体耗时算子 → 检查该算子的 tile/同步/精度实现是否带有 CUDA 惯性假设 → 用 AOE 或手动重写关键路径。**

#### 一、先判断瓶颈类型

用目标平台的 Profiling 工具（昇腾 msProf / 海光 rocprof）采集数据，看 Roofline 图：

- **访存受限**：大部分时间在等内存，需优化数据搬运通路和重复搬移。
- **计算受限**：计算单元接近饱和，需换计算单元、降精度或减少计算量。
- **流水利用率低**：未达硬件上限，问题在流水编排和同步策略。

#### 二、排查四类 CUDA 惯性假设

**1. 共享内存 Tile 尺寸假设**
CUDA 常动态配置 shared memory tile，但部分国产芯片的共享缓冲区是固定大小（如昇腾 L0B 固定 32KB）。硬编码 CUDA 风格 tile 会导致数据溢出到更慢的层级。

**2. 同步与流水编排假设**
CUDA 的 `__syncthreads()`、异步拷贝语义在国产芯片上可能不同。算子融合时，本可并行的算子可能因保序约束被强制串行化，导致性能骤降。

**3. 编译期决策已固化**
部分平台（如昇腾 ATC）在编译阶段就固化了 tiling 策略和实现选择，运行时无法更改。若编译期选错实现，只能重新编译或用 AOE 调优。

**4. 线程/并行粒度不匹配**
CUDA 是 32 线程 Warp，部分国产芯片是 64 线程 Wavefront。依赖 `warpSize=32` 的逻辑会重复计算或空转，结果正确但性能折半。

#### 三、用 Profiling 数据定位

重点看：MTE/Vector/Cube cycle 占比（判断瓶颈单元）、UB/L1 实测带宽（是否远低于理论值）、bank 冲突率、L2 命中率。昇腾 MindStudio Insight 的 Top Warp Stall Reason 可直接看流水线停顿主因。

### 如果目标平台没有完全对应的 Tensor Core 指令怎么办？
答：
如果目标平台没有完全对应的 Tensor Core 指令，我会从计算语义、硬件能力和性能收益三个方面评估，不会直接照搬原平台的指令实现。

第一，寻找等价计算路径。如果目标平台有类似矩阵计算单元，就使用其对应的矩阵乘法指令或高性能算子库，重新适配 Tile 大小、数据类型、线程布局和数据搬运方式。

第二，调整算法和数据精度。如果矩阵指令支持的精度或计算形状不同，可以考虑 FP16、BF16、INT8 等目标平台支持的数据类型，并验证精度误差；如果没有合适的矩阵计算单元，就使用 SIMD/SIMT、向量化指令或普通计算单元实现矩阵乘法。

第三，重新进行性能调优。根据目标平台的计算吞吐量、访存带宽、寄存器和 Shared Memory 容量，调整分块策略、数据复用和并行粒度，并通过 Benchmark 和 Profiling 确定最优实现。

最后，我会验证数值精度、边界条件和端到端性能，确保替代实现不仅能够正确运行，而且在目标平台上具有实际收益。

面试总结： Tensor Core 是一种硬件实现方式，而不是算法本身。迁移时应保留计算语义，根据目标平台的硬件能力重新选择指令、数据精度和并行策略；如果缺少等价硬件，就采用通用计算路径，并通过实测权衡性能与精度。

### 如何确保跨平台精度一致？
答：我会从统一计算语义、控制数值误差、分层验证和端到端回归四个方面确保跨平台精度一致。

第一，统一计算语义，包括输入输出的数据类型、累加精度、量化参数、舍入模式、溢出处理以及算子实现中的边界条件，避免不同平台因计算规则不同产生误差。

第二，控制数值误差。对于 FP32、FP16、BF16、INT8 等不同精度路径，明确允许的误差范围；如果目标平台使用不同的矩阵计算指令或累加精度，需要评估误差是否会逐层累积，必要时采用更高精度累加或对敏感算子使用混合精度。

第三，建立分层验证机制。先验证单算子的输出误差，再验证模型中间层输出，最后比较端到端结果。常用指标包括最大绝对误差、最大相对误差、RMSE，以及任务相关指标，例如分类准确率或检测 mAP。对于接近零的数值，相对误差可能失去参考价值，因此需要结合绝对误差判断。

第四，进行自动化回归测试。覆盖不同 Tensor Shape、边界条件、随机输入和极端输入，并在固定测试集上比较各平台结果。对于量化模型，还要验证校准参数、量化与反量化过程及最终任务精度。

面试总结： 跨平台精度一致不一定意味着每个浮点数逐位相同，而是要保证计算语义一致、数值误差在约定阈值内、端到端任务指标满足要求。如果业务要求确定性或逐位一致，则还需要进一步统一运算顺序、舍入规则和确定性算法。浮点加法具有非结合性，不同硬件的指令调度和累加顺序都可能造成细微差异。

### PagedAttention 与 Continuous Batching
答：
PagedAttention 解决的是 KV Cache 的存储与寻址问题：把每个请求的 KV Cache 切分成固定大小的物理 Block，通过 Block Table 将逻辑 Token 位置映射到物理存储位置，从而减少连续大块内存分配带来的浪费，并支持动态增长和跨请求管理。

Continuous Batching 解决的是请求调度问题：每一步生成后，根据完成、到达和资源变化动态调整参与执行的请求集合，而不是等一个固定 Batch 全部完成后再启动下一批。

两者协同后，推理系统既可以动态调度请求，也可以更灵活地分配 KV Cache。但需要注意，PagedAttention 本身不等于 Attention 算法优化，FlashAttention 也不等于 KV Cache 管理系统。

### FlashMLA、MLA 与 SparseAttention
答：
- MLA（Multi-head Latent Attention）：通过压缩或低维潜在表示降低 KV Cache 的存储开销，DeepSeek 系列模型是典型应用背景。
- FlashMLA：针对 MLA 相关计算和 KV Cache 组织进行优化的 Kernel 实现，具体支持的硬件、数据类型和功能取决于实现版本。
- SparseAttention：通过稀疏连接、局部窗口或选择性访问减少实际参与计算的注意力元素；它可能改变计算量，但通常不再等价于原始的全量稠密 Attention。

### 将 vLLM 移植到沐曦，需要改什么？
答：将 vLLM 移植到新芯片，核心是适配底层硬件运行时、补齐关键算子实现，并保证 KV Cache 管理、请求调度和分布式推理能够正确运行，最后针对沐曦硬件进行性能优化。我会分六个层次推进。

1. **设备与运行时层：** 适配设备发现、内存分配、Stream/Event、算子注册和设备后端，优先使用沐曦官方 MXMACA 软件栈及已有适配组件，减少重复开发。
2. **算子层：** 重点检查 Attention、RMSNorm、RoPE、GEMM 和 Sampling 等算子的兼容性与性能。如果现有算子库不支持，就基于目标平台的编程模型重新实现，并通过分块、数据复用、算子融合等方式优化。
3. **KV Cache 层：** 适配 Paged KV Cache 的物理 Block 分配、Block Table、Cache Append、寻址和释放逻辑，确保 Prefill、Decode 及动态请求场景下的数据读写正确。
4. **调度层：** 验证 Continuous Batching、请求生命周期管理、显存容量约束和抢占策略，确保请求动态加入、完成和资源回收时，调度状态与 KV Cache 状态保持一致。
5. **模型与精度层：** 检查权重加载、数据类型、量化路径和模型算子覆盖情况，通过单算子误差、中间层输出和端到端任务指标验证数值精度。
6. **测试与性能层：** 从单算子、单模型逐步扩展到长序列、并发请求和多卡场景，评估 TTFT、TPOT、吞吐量、显存占用及稳定性，再根据 Profiling 结果定位计算、访存、调度或通信瓶颈。

对于 Paged KV Cache，重点难点是 **Block 的分配与回收、并发请求下的生命周期管理、最后一个 Block 的有效长度、Block Table 更新、Prefix Cache 共享，以及内存碎片和容量控制**。特别是 Prefix Cache 共享场景，需要通过引用计数或等价的生命周期管理机制，避免一个请求释放仍被其他请求引用的 Block；同时要保证异步 GPU 操作完成前不会提前复用相关内存。

整体策略是先确认官方适配栈，完成基础推理和正确性验证，再逐步补齐算子、KV Cache、调度及分布式能力，最后基于实际负载进行性能优化，而不是简单地替换 CUDA API。
