“合并访存”（Memory Coalescing）是并行计算体系结构中，尤其是 **GPU（如 NVIDIA CUDA）** 中的一个核心性能概念。它描述的是：**同一执行单元中的多个线程，其对全局内存的访问是否能够被硬件合并为尽量少的内存事务**。合并得越好，带宽利用率越高，访存延迟越低，程序性能越好。
## 一、硬件背景与基本概念
### 1. GPU 执行模型
- GPU 以 **Warp**（NVIDIA 中通常为 32 个线程）为基本执行单元。
- Warp 中的线程 **SIMT（Single Instruction, Multiple Threads）** 同步执行。
- 当 Warp 中线程执行一次全局内存 load/store 指令时，硬件会尝试将这些访问 **合并（coalesce）** 成尽可能少的内存事务。
### 2. 内存事务（Memory Transaction）
- GPU 全局内存以 **cache line / memory segment** 为单位访问（常见为 32B、64B、128B，具体取决于架构）。
- 如果一个 Warp 的 32 个线程访问的地址落在 **同一个或少数几个连续的内存段** 中，就可以用少量事务完成。
- 若访问分散，则需要多个事务，导致带宽浪费。
## 二、什么是合并访存
**合并访存**指的是：
> 一个 Warp 中多个线程对全局内存的访问，能够被硬件自动合并为尽量少的、对齐的内存事务。
核心目标：
- 减少内存事务数量
- 提高内存带宽利用率
- 降低访存延迟
## 三、典型的合并与非合并访问模式
### 1. 理想的合并访存（连续访问）
```c
int tid = blockIdx.x * blockDim.x + threadIdx.x;
float x = A[tid];
```
- 线程 0 访问 A[0]
- 线程 1 访问 A[1]
- …
- 线程 31 访问 A[31]
特点：
- 地址连续
- 类型大小一致（float = 4B）
- 总跨度 32 × 4B = 128B
结果：
- 通常只需要 **1 次或极少次数内存事务**
- **完全合并**
### 2. 跨步访问（Stride Access，部分或非合并）
```c
float x = A[tid * 2];
```
- 地址间隔为 8B
- Warp 覆盖的地址范围扩大到 256B
结果：
- 需要更多内存事务
- 带宽利用率下降
### 3. 完全非合并（随机访问）
```c
float x = A[index[tid]];
```
- 每个线程访问不相关的地址
- 地址分布不可预测
结果：
- 每个线程可能触发独立事务
- 性能极差（典型的 memory-bound）
## 四、合并访存的关键规则（以 NVIDIA CUDA 为主）
> 具体细节随架构变化，但总体原则一致。
### 1. 访问粒度与对齐
- 访问类型（char / int / float / double）决定访问粒度
- 内存地址应 **自然对齐**
    - float：4B 对齐
    - double：8B 对齐
不对齐会导致额外事务。

| 访问类型                 | 单次事务典型粒度         | 说明        |
| -------------------- | ---------------- | --------- |
| 普通 global load/store | **128B**         | 合并访存核心单位  |
| 只读 / texture load    | 32B / 64B / 128B | cache 决定  |
| 向量化 load（float4）     | 多个 128B          | Warp 覆盖更大 |
| atomic               | 无固定粒度            | 序列化为主     |
| constant memory      | 32B（广播）          | 同址 1 次    |
### 2. Warp 内线程访问模式
- **同一 Warp 内** 是否合并，完全由 **线程地址分布** 决定
- 不同 Warp 之间互不影响
### 3. 结构体与数组（AoS vs SoA）
#### 非理想（Array of Structures）
```c
struct Particle {
    float x, y, z;
};
Particle p[N];
float x = p[tid].x;
```
- 访问间隔为 sizeof(Particle)
- 不利于合并
#### 理想（Structure of Arrays）
```c
float x[N], y[N], z[N];
float vx = x[tid];
```
- 连续访问
- 高度合并
### 4. Cache 的影响
- 新架构中（如 Volta 以后），L1 Cache 能缓解部分非合并访问
- 但 **不能替代良好的合并访存设计**
- 合并差仍然会导致带宽浪费
## 五、合并访存与共享内存的关系
- **全局内存**：高度依赖合并访存
- **共享内存（Shared Memory）**：
    - 延迟低
    - 不存在合并访存问题
    - 但存在 **Bank Conflict**（类似但不同的问题）
常见优化策略：
1. 从全局内存合并读取
2. 写入共享内存
3. 在共享内存中进行复杂、非连续访问
## 六、性能影响（为什么合并如此重要）
假设：
- 理想情况下：1 个 Warp = 1 次 128B 事务
- 非合并情况下：1 个 Warp = 32 次 32B 事务
结果：
- 实际带宽可能下降一个数量级
- Kernel 明显 memory-bound
- SM 计算单元大量空闲
## 七、常见反模式（Anti-patterns）
1. 使用线程 ID 作为二维数组的列索引（行主序存储）
2. 在 Warp 内做散列（hash）访问
3. AoS 数据布局
4. 未对齐的 double / vector load
5. Warp 内条件分支导致不同访问模式
## 八、优化合并访存的实践建议
1. **保证 Warp 内连续访问**
2. 使用 **SoA 数据布局**
3. 让 threadIdx.x 对应连续内存
4. 尽量使用 `float4 / int4` 等向量化加载
5. 必要时通过共享内存重排数据
6. 使用 Nsight Compute / Nsight Systems 检查：
    - Global Load Efficiency
    - Memory Transactions per Request
## 九、一句话总结
> 合并访存的本质，是让一个 Warp 的线程“像一个宽向量”一样访问内存；  
> 访问越连续、越对齐、越规则，GPU 就越快。
